## 0. 背景：为什么要有这份方案（实证，非猜测）

本次在 v6 上跑完整链路验证（probe → generate → run），结果：

| 步骤 | 结果 |
|---|---|
| probe | ✅ 6 个交互元素 |
| generate | ✅ 5 用例 → test_cases.py + 5 datasets |
| run **串行** | ✅ **5 passed in 5.87s** |
| run **并发 `--workers 2`** | ❌ **2 failed / 3 passed**（`Locator.click: Target crashed`） |

### 0.1 根因：内核 OOM-kill（dmesg 实证，非推断）

```
oom-kill:constraint=CONSTRAINT_NONE,...,global_oom,task_memcg=/user.slice/.../session-695.scope,task=chrome-headless,pid=181683
Out of memory: Killed process 181683 (chrome-headless) total-vm:55070844kB, anon-rss:14576kB
Out of memory: Killed process 64593 (hermes) task_memcg=/system.slice/hermes-gateway-<profile>.service
```

两个后果：
1. 渲染进程被杀 → Playwright 报 `Target crashed`（2 个用例失败）；
2. **连带把 `hermes-gateway-<profile>.service` 的 Hermes 进程也杀了**（systemd 已自动拉回：`active, NRestarts=1`）。

### 0.2 资源实测（本机）

| 指标 | 实测值 |
|---|---|
| MemTotal | 1,915,896 kB ≈ **1.87 GB** |
| SwapTotal | **0**（无交换，无缓冲余量） |
| MemAvailable（跑测试前） | ≈ **793 MB** |
| Hermes 自有进程 RSS 合计 | ≈ **828 MB**（4 个 hermes 进程） |
| **1 个 headless Chromium 实例**（playwright driver + chromium 全树） | **≈515 MB / 7 进程**（多轮实测 513~516MB；单次最低读到 383MB，不可信） |
| 2 个实例（推算） | ~**1030 MB** ⇒ 远超可用内存（实测强跑 2 worker 即 OOM） |
| CPU 核数 | **2** |

### 0.3 三条关键结论

- **真凶是 `cli.py:131` 的默认值 `-n auto`**：`nproc=2`，所以不显式传 `--workers` 时 pytest 会起 **2 个 worker**，每个 ~515MB ≈ 1030MB，直接吃穿仅剩的 ~700MB。
- **`/dev/shm` 不是问题**：936MB、使用率 0%，排除"shared memory 太小"那类经典坑。
- **代码没问题**：同样这两个用例串行单跑 2/2 PASSED，全部 5 个串行 5/5 PASSED。定位逻辑、断言、用例设计均正常。

### 改动 1 🟡 — 统一 Chromium 启动参数（降耗 + 消除 8 处不一致）

**现状**（8 处裸 `launch`，参数全空）：

| # | 位置 | 代码 |
|---|---|---|
| 1 | `framework/cli.py:47` | `p.chromium.launch(headless=True)` |
| 2 | `framework/cli.py:96` | `p.chromium.launch(headless=True)` |
| 3 | `framework/generator.py:149` | `p.chromium.launch(headless=True)` |
| 4 | `framework/generator.py:255` | `p.chromium.launch(headless=not _headed)`（conftest 模板） |
| 5 | `framework/runner.py:92` | `p.chromium.launch(headless=headless)` |
| 6 | `framework/runner.py:124` | `p_.chromium.launch(headless=True)` |
| 7 | `framework/explorer.py:150` | `p.chromium.launch(headless=True)` |
| 8 | `scripts/conftest.py:49` | 生成物（同上 #4 模板产出） |

**改法**：新增 `framework/browser.py`，作为唯一事实来源：

```python
"""Chromium 启动参数唯一来源（降耗 / 低内存稳定）。"""
from __future__ import annotations
import os

# 基础瘦身参数：与业务无关，纯降耗（实测约省 10~20% RSS）
CHROMIUM_ARGS = [
    "--disable-dev-shm-usage",           # 用 /tmp 替代 shm（低内存/容器稳）
    "--disable-gpu",                     # 无头无需 GPU
    "--disable-extensions",              # 不加载扩展
    "--no-first-run",
    "--no-default-browser-check",
    "--disable-background-networking",
    "--disable-backgrounding-occluded-windows",
    "--disable-renderer-backgrounding",
    "--renderer-process-limit=1",        # 限制子进程数（2 实例曾达 12 进程）
]
# ⚠️ 实测更正：本组参数**不降低 RSS**（裸参/全参数同为 513~516MB）。价值在稳定性/一致性。

def launch_opts(headless: bool = True) -> dict:
    """返回 p.chromium.launch(**launch_opts(headless=...)) 的参数字典。"""
    args = list(CHROMIUM_ARGS)
    heap = os.environ.get("HYBRID_JS_HEAP_MB")      # 可选：限制渲染进程 V8 堆
    if heap:
        args.append(f"--js-flags=--max-old-space-size={int(heap)}")
    return {"headless": headless, "args": args}
```

改用：

```python
from framework.browser import launch_opts
b = p.chromium.launch(**launch_opts(headless=True))
```

**为什么有效（已按实测更正）**：本组参数**不降 RSS**（实证见第 0 节更正），价值在**稳定性与一致性** ——
禁掉扩展下载（browser-use 默认会下 uBlock 卡内网）、去掉 GPU 路径、shm 落 /tmp（容器里 /dev/shm 常只有 64MB）、
限制子进程数。`HYBRID_JS_HEAP_MB` 让"堆上限"可按被测页复杂度调（**默认不开**，避免重业务页把 tab 顶崩——见风险 R1）。

| 项 | 说明 |
|---|---|
| 影响面 | 8 处 + 1 个新文件 |
| 回滚 | 删除 `framework/browser.py` 并把 8 处改回裸 `launch`（git 无版本库，回滚靠 `v6` 包解包覆盖） |

### 改动 2 🔴 — worker 自动降级 + 内存预检（**决定性修复**）

**现状**：`framework/cli.py:131`

```python
cmd += ["-n", str(workers)] if workers else ["-n", "auto"]   # ← 默认 auto = nproc = 2，OOM 元凶
```

**改法 A**：新增 `framework/limits.py`

```python
"""低内存环境下的并发安全闸（防内核 OOM 误杀 Hermes 网关）。"""
from __future__ import annotations
import os
from pathlib import Path

PER_WORKER_MB = int(os.environ.get("HYBRID_MB_PER_WORKER", "550"))  # 观测上界 515MB + 余量
RESERVE_MB    = int(os.environ.get("HYBRID_RESERVE_MB", "450"))     # 留给 Hermes 网关 + OS

def mem_available_mb() -> int:
    for line in Path("/proc/meminfo").read_text().splitlines():
        if line.startswith("MemAvailable:"):
            return int(line.split()[1]) // 1024
    return 0

def safe_workers(requested: int | None = None) -> tuple[int, str]:
    """返回 (安全并发数, 人类可读理由)。"""
    avail = mem_available_mb()
    by_mem = max(1, (avail - RESERVE_MB) // PER_WORKER_MB)
    by_cpu = len(os.sched_getaffinity(0)) if hasattr(os, "sched_getaffinity") else 2
    cap = max(1, min(by_mem, by_cpu))
    want = requested or cap
    final = min(want, cap)
    why = (f"MemAvailable={avail}MB, 每worker预算={PER_WORKER_MB}MB, 系统保留={RESERVE_MB}MB, "
           f"CPU={by_cpu}核 → 安全并发={cap}"
           + (f"; 请求 {want} → 降级 {final}" if final < want else ""))
    return final, why
```

**改法 B**：`cli.cmd_run` 接入

```python
def cmd_run(workers=None, headed=False, force_workers=False):
    ...
    n, why = safe_workers(workers)
    print(f"[run] 资源预检: {why}")
    if not force_workers and workers and workers > n:
        print(f"[run] ⚠️ 并发 {workers} 超出安全值 → 降级 {n}（如确有把握可用 --force-workers 覆盖）")
    cmd = [sys.executable, "-m", "pytest", str(tests), "-v",
           f"--html=log/{run_id}/report.html", "-s", "-n", str(n)]
```

**为什么有效**：把"起几个浏览器"从**猜**变成**按可用内存算**。以本机当前值验证：`(793-450)//400 = 0 → max(1,0) = 1` → 自动降到 **1 worker**，正是实测安全的档位。这是本次 OOM 的**决定性修复**（改动 1 只是降耗增效）。

| 项 | 说明 |
|---|---|
| 影响面 | `cli.py`（默认值 + 新开关）、新文件 `limits.py` |
| 新增 CLI | `--force-workers`（逃生口，绕过预检） |
| 回滚 | 把 `-n` 分支改回 `auto` |

### 改动 3 🟢 — 逐用例日志：按 run-id 分目录（每次运行干净）

**现状**：`framework/generator.py:287`（conftest 模板）与生成物 `scripts/conftest.py:81` 都是**追加模式**：

```python
with open(LOG_DIR / f"{case_id}.log", "a", encoding="utf-8") as f:
```

后果：跨多次运行累积。实测现在 `log/` 里 5 个用例共 **704 行**（`create_bu_a_c1.log` 已 200 行，混了好几天），出问题时要靠猜哪几行属于本次。

**改法**：
- `cli.cmd_run` 生成 `run_id = datetime.now().strftime("%Y%m%d_%H%M%S")`，经环境变量 `HYBRID_RUN_ID` 传给 pytest；
- conftest 的 `_append_log` 写到 `log/<run_id>/<case_id>.log`（**不传时落到 `log/latest/` 并在会话开始清空**，保证单跑也干净）；
- 同一次运行的 pytest 报告也归到 `log/<run_id>/report.html`，运行证据自包含。

**为什么有效**：天然"每次运行干净"，且保留历史 run 可对比（比"覆盖同一文件"更有取证价值）。

| 项 | 说明 |
|---|---|
| 影响面 | `cli.py`、`generator.py` 模板、`scripts/conftest.py`（重跑 generate 覆盖） |
| 同步文档 | `README.md`、`build_html.py` 静态文案、`training.html`（改完必须 `python build_html.py` 重跑） |
| 回滚 | 改回 `LOG_DIR / f"{case_id}.log"` + `"a"` |

### 改动 5 🟢 —（建议一起做，可拆）demo 服务并发化

**现状**：`demo/app.py:32` 用 `socketserver.TCPServer`（**单线程**），2 个 worker 并发时请求排队 → 放大超时抖动。

**改法**：换 `socketserver.ThreadingTCPServer`（一行 + 保留 `allow_reuse_address`）。

**为什么**：让"被测应用"不再成为并发瓶颈，测出来的问题才是真问题。

---

### 改动 6 🟢 —（可选，系统层，需 sudo）保护 Hermes 网关不被 OOM 误杀

**理由**：本次 OOM 是 `global_oom`，内核挑内存大户下手，Hermes 是最大户（277MB+235MB+199MB+117MB）→ 被连带杀掉。

**改法**：给 Hermes 服务加 `OOMScoreAdjust=-500`（systemd drop-in），降低被杀概率。属操作系统层、不在框架内，**待你确认是否要动**（需 root）。
