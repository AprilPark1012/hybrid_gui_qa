1为什么是「混合」？

一桌子两把刀，各有锋利处，别只拿一把。

[ai] Browser Use（AI）

  • [OK] 听得懂人话
  • [OK] 会规划步骤、挑元素
  • [NG] 会"幻觉"，结果不总重复
  • [NG] 每步花一次模型钱（token）
1+1>2

[OK] Playwright（确定）

  • [OK] 精准、不猜、可回归
  • [OK] 免费、快、能进 CI
  • [NG] 不透人性，得人写 selector
  • [NG] UI 一改 selector 就断
生活类比：AI 是导游——认得路、会安排行程，但可能带偏；
Playwright 是导航仪——绝对准、说走就走，但得先输入目的地。
[*] 导游负责规划，导航仪负责走稳——这就是我们要的配合。

新员工怎么用这份地图找东西

(1) 想知道某步跑什么逻辑 -> 看 framework/ 对应模块；
(2) 想改测试数据 -> 改 cases/ 下的用例 json（再跑 generate 重建 scripts/）；

3整体流程：explore(AI 产用例) -> cases/ -> generate -> run(带自愈)

本框架有两种业务场景：(1) 自然语言 -> `explore --ai` 语义识别/编排 -> 用例落 cases/ai_*.json（花 token）；(2) 手搓 cases/*.json -> `generate` 生成脚本+数据分离 -> `run` 执行（零 token）。一条龙（`cli all`）跑的是确定性执行那条；两条链路在 cases/*.json 汇合。

[ai] AI 分支：`cli explore --ai`（AI 语义识别，需 DeepSeek key）

给一句自然语言场景，AI 读场景 + probe 语义清单 + DOM 上下文 -> 挑对控件 -> 产出 ElementMap（步骤+语义引用），并默认同步落 cases/ai_*.json（--no-cases 可关）。generate 会读它、优先消费 element_map 快照，AI 用例与手写用例走同一条确定性执行链路。
三道防假安全感闸：(1) 交付即验证——落盘后默认 --verify 立刻试跑该用例，实测 PASSED 才算出活，FAILED 就 [NG] + exit 3（日志 output/verify/）；(2) AI 失败即报错退出（exit 2），绝不静默用 mock 顶替（mock 只在显式 --mock-fallback 出现且不入库）；(3) 落盘前用例质量校验拦「断言=输入回显」与「断言=猜出来的运行时计数（共 N 条）」。
另有：DeepSeek function calling 有间歇性 JSON 抖动 -> 内置退避重试（HYBRID_LLM_ATTEMPTS 默认 3）；cli prune 给快照做归档保留（各留最近 N 个）。
场景文件：--scenario-file / --scenario-dir 直接读 scenarios/*.yml（一文件=一场景，含 business_context 领域知识 与 assert_guard 断言护栏），与内联 --scenario 共用同一条下游链路。

4先让 AI 出题，再按需手搓（两种业务场景）

主推路径是 AI 链路：你写自然语言场景（scenarios/*.yml）， AI 负责语义识别、编排步骤、识别控件，产出可执行用例。 手搓用例降级为调试/回归辅助——用在「需要精确断言 / 补一条边界负向 / 把 AI 产出固化成回归资产」这些场合。 两条链路在 cases/*.json 汇合：那是它们唯一的接口。 汇合之后完全同一条链（generate -> run）， 这就是「AI 产的用例」和「你手搓的用例」能跑同一条执行链、拿到同一份报告的原因。

4.1 先分清两条链路（主推 AI；手搓做辅助）

场景(1) · 场景驱动（AI 语义识别）场景(2) · 用例驱动（直接写用例）
你要准备的文件 scenarios/<模块>/<场景id>.yml
自然语言动作流（人话）		 cases/manual/<用例id>.json
结构化步骤 + 断言（机器话）
入口命令 python -m framework.cli explore --ai --scenario-file … python -m framework.cli generate && … run
产出 cases/<场景id>/ai_<场景id>_<HHMMSS>.json（AI 写的用例，按场景分目录） 直接进 scripts/generated/<场景id>/<用例id>.py（无中间产物）
花不花 token 花（每次跑都调 LLM；离线机器用录像回放，见第 6 章） 零 token（纯确定性，可反复跑、可进 CI）
什么时候用 默认从这里开始：页面/口径已清楚，要批量铺覆盖（一个场景 × N 组数据 = N 条用例）； 或者你想先让 AI 试一遍看它怎么选控件 边界与负向（点错该失败、空值该拦截）、要精确断言、临时补一条、 以及把 AI 产出的满意用例固化成回归资产
推荐节奏 先写场景跑通 -> 看 AI 产出的用例 -> 满意就固化成 cases/<id>.json（去掉 ai_ 前缀）-> 之后当回归资产零成本重跑 抄一份最像的现成用例改（别从零写）

一句话：场景(1) 前期花 token 换覆盖速度；场景(2) 零成本换精确度。两者产出的用例格式完全相同，随时可以互相转换。

4.2 场景文件 scenarios/<模块>/<场景id>.yml

一个文件 = 一个场景；文件名 = 场景 id（小写蛇形，正则 ^[a-z][a-z0-9_]*$）。 目录按业务模块分（如 scenarios/contracts/、scenarios/orders/）。 只有 scenario 字段是必填的，其余按需。

最小可跑样例（照着改就行）

# 一个文件 = 一个场景；文件名 = 场景 id
id: orders_invoice_full_lifecycle
title: 合同列表 · 按编号搜索
description: 输入合同编号片段 -> 点搜索 -> 确认列表出现对应编号的记录
tags: [合同, 搜索, smoke]
priority: P0
owner: AprilPark1012
updated: 2026-09-21

target:
  url: http://localhost:8000
  page: 合同列表页（合同列表 + 多条件搜索 + 新建弹窗）
  preconditions:
    - demo 已启动：python -m demo.app

# —— AI 语义识别的输入：自然语言动作流 ——
scenario: |
  在合同列表页面的搜索框输入 '{关键词}'，点击搜索按钮，
  确认结果列表里出现编号为 {期望编号} 的合同记录。

# —— 数据参数化：一组数据 = 一条用例（报告里独立一行）——
# 占位符写在 scenario 文案里，这里每组给一组值；
# 组值必须**恰好**覆盖文案里用到的占位符（少了会被拦）。
# id 可选：给了就进报告里的用例名（如 test_xxx[编号-1007]），便于单组定位。
data:
  - {id: "编号-1005", 关键词: "1005", 期望编号: "HT-1005"}
  - {id: "编号-1007", 关键词: "1007", 期望编号: "HT-1007"}

# —— 领域上下文：帮 AI 挑对控件、判断数据规则 ——
business_context: |
  关键字搜索框的 placeholder 是“合同编号/名称/管理单元/合同类型/帐套”，名称列模糊匹配；
  合同编号规则 HT-1000+i（输入片段 1005 -> 目标记录编号 HT-1005）；
  页面底部状态行文案形如“搜索完成，命中 N 条”——N 是运行时才知道的，不作断言。

# —— 断言护栏：事前喂给 AI，事后落盘硬校验 ——
assert_guard:
  must_contain:
    - "{期望编号}"     # 数据驱动后护栏也走占位符
  forbidden:
    - "命中"           # 计数文案不许进断言

写场景的四条写作要点（血泪教训）

  1. 断言必须「操作前可确定」：写记录标识（HT-1005）或页面固定文案， 别写运行时才知道的计数（共 N 条）。全局已禁计数/时间戳/随机值， assert_guard 里可再加本场景专属禁令。
  2. business_context 越具体，AI 挑控件越准：把 placeholder、可选值、编号规则写进去。
  3. must_contain 会双向生效：事前告诉 AI 该围绕什么写断言，事后校验断言是否真的验到了它。
  4. 场景跑不通时，先改场景文件（这是正常的编写循环），而不是去改框架。 只有当「框架真的缺能力」时才动框架 —— 判断标准：同一个卡点是否在多个场景反复出现。

写场景前必知的 demo 三件事

  1. 数据在服务端：列表页与详情页读的是同一条真实记录 -> 预置数据的字段跨页一致，可以断言； 查不到的编号会如实报「未找到」，不会编数据。
  2. 每条用例开始前框架会复位数据 -> 列表页固定 20 条预置； 别写「上一条用例新建的数据留给下一条用」这种跨用例依赖（复位后就不存在了）。
  3. 客户字段是「弹层列表里选一行」：弹层里多个「选择」按钮文字完全相同 -> 语义名形如 选择@北京华信科技有限公司；列表页客户筛选是右模糊（前缀）匹配（非前缀不命中）。

4.3 用例文件 cases/<用例id>.json

顶层只有 5 个字段：case_id（唯一 id，也是产物里测试函数名的来源）、 name（报告里显示的名字）、base_url、 steps（动作序列）、asserts（断言序列）。 AI 产的用例（ai_*.json）和你手搓的格式完全一样。

steps：支持的 7 个动作（照抄即用）

op必填说明
gotourl打开页面（一般每个用例第一步）
clickelement点击；element 是语义名（见下）
fillelement + value填输入框；value 支持 {datetime} 一类占位符
selectelement + value下拉选择
checkelement勾选/取消勾选（幂等，不要求当前状态）
press_enterelement在输入框按回车触发（表单提交/搜索）
expect_texttext文本类断言动作（AI 产出路径会用它落断言）

每个 step 都建议写 desc（人话描述）—— 它会进用例日志，失败时是给同事看的第一手线索。

asserts：断言类型（kind）

kind写什么语义
countselector + expect命中行数/元素数等于 N（最常用，如「筛完只剩 1 条」）
textelement 或 selector + expect元素文本包含/等于期望值
value同上输入框的当前值
visible / hiddenelement 或 selector元素可见 / 不可见（弹层开合、错误提示是否出现）
enabled / disabled同上按钮可点 / 置灰（负向用例主力：必填没填时提交该置灰）
checked / unchecked同上勾选框状态
attrselector + name + expect属性值（如 data-field）
urlexpect当前地址（跳转/带参跳转）
first_rowselector + expect取第一行做比对（排序类断言）

断言可以多条并存（一个用例 = 一串断言），失败时报告会指出是哪一条。断言是唯一的判定依据 —— 操作步骤成功不等于测试通过。

[!] 最关键的一处约定：element（语义名）从哪来

语义名不是 selector，也不是 testid，而是「页面上这个控件叫什么」的稳定说法： 

语义名 = 页面上可被"读"到的身份，按优先级取：
        placeholder  ->  role + name  ->  控件可见文本  ->  title / aria-label
        例：'请输入合同名称'（placeholder）· '搜索'（按钮文本）· '选择@北京华信科技有限公司'（弹层选行）

怎么查到它们：跑 python -m framework.cli probe， 它把页面（含弹层及其内嵌挑选层）的可交互元素翻译成语义清单，落到 output/element_maps/probe_*.json。 手搓用例前先跑一次 probe，照着清单抄语义名 —— 别猜。

口径与生产一致：被测系统里只有顶层容器带 testid，控件层没有。 所以手搓时不要指望用 testid 定位控件；语义名命中不唯一时，框架会如实报歧义并要求你给更精确的定位 （加容器锚点/字段步/title），不会按顺序猜第一个——这是刻意设计，避免"点错元素还绿"。

手搓一个用例：五步

# (3) 生成脚本（幂等，可反复跑）

4.4 两个文件的共同约定（团队要背的六条）

约定为什么 / 怎么做
(1) 只改源头，不改产物 scripts/generated/（一个用例一个脚本： <场景id>/<用例id>.py + manual/ + _harness.py + conftest.py + index.json）、 scripts/datasets/*.json 都是 generate 的产物， 手改会被下一次 generate 覆盖。要改行为 -> 改 cases/*.json 或 scenarios/*.yml，然后重新 generate。
(2) 断言必须「操作前可确定」 禁计数（共 N 条）、时间戳、随机值 —— 这类断言要么永远为真（假绿），要么随机红。
写记录标识（HT-1005）、固定文案、或你自己造的数据。
(3) 不许跨用例依赖 每条用例开始前框架复位数据 ->「上一条建的记录」不存在。需要前置数据就在自己的 steps 里造。
(4) 定位不唯一要如实报错 语义名命中多个 -> 框架报歧义、要求更精确的定位（容器锚点 / 字段步 / title）， 绝不按顺序猜。你看到歧义报错时，是它在保护你，不是它坏了。
(5) 元素口径对齐生产 只有顶层容器有 testid，控件层没有 -> 手搓时用语义名，不用 testid 定位控件。
(6) 交付前自检 python -m framework.cli generate（必须 0 未映射）-> python -m pytest tests/_helpers/（一类）-> python tests/_runner/run_verifications.py（二类）。 三条全绿才算改完。

这四段为什么这么分工（记住这 6 句，谁的责任就清楚了）

[nav]

(1) cli 只做入口与串联

cli 不写业务：解析参数（三入口互斥）-> 备好场景/URL/护栏/用例名 -> 交给 _explore_one；最后负责「交付即验证」与归档清理。

[look]

(2) probe = 眼睛（感知，0 token）

只回答「页面上有哪些控件、它们各叫什么、怎么区分」。产 semantic_name + 消歧上下文； 不决策、不规划、不产 selector、判不了唯一性（唯一性是执行期 locator_bridge 的事）。

[brain]

(3) explorer = 大脑（认知，花 token）

只回答「这一步该动哪个控件、填什么、拿什么当断言」。它必须先让 probe 探两次（基础页 + 弹窗）， 否则看不到表单字段；拿到清单后交给 LLM 决策，再把名字对齐成 probe 的元素引用。

[handshake]

(4) 两者靠一个契约见面：semantic_name

probe 起名（保证唯一）-> AI 引用它 -> 写进 cases 的 element -> generate 拿它查 loc_map -> 变成 locator。selector 从头到尾不进 LLM，这就是"AI 理解、代码定位"的落地方式。

[loop]

(5) probe 出场两次、同名不同用途

explore 时（出场(1)）是「给 AI 看菜单」；generate 时（出场(2)）是「把名字翻译成 locator」。 默认优先用 explore 留下的 element_map 快照，避免重复探测、 也躲开"弹窗要打开/元素时序不稳"的坑。

[guard]

(6) 三道闸门挂在哪

防假 AI：ai_explore 拒绝 mock 冒充（exit 2）； 防假绿：case_warnings（回显/计数/缺元素/护栏）+ generate 的未映射即 fail； 交付即验证：_verify_cases 实测通过才算数（exit 3）。

[!] 读这张图时最容易踩的 4 个坑（都实测过）

1. 同步/异步边界：阶段A（Playwright 同步 API）必须在事件循环之外跑。写进 async 函数里会抛 "Sync API inside the asyncio loop"，再被静默兜底 -> 弹窗字段和 DOM 上下文全丢（曾长期如此）。
2. 别重复探测：cli 探一次、ai_explore 内部再探一次 = 连开两个 Chromium，内存紧时第二个起不来。 现在只由 ai_explore 探一次。
3. element 必须写 probe 的 semantic_name（不是人话名，如"搜索"-> 探测名可能带前后缀）。 写错不会静默通过：generate 会告警并在脚本里 pytest.fail。
4. 快照会过期：element_map / probe 快照是"某一次探测的固化"，页面改版后要用 --live-probe 或重新 explore 刷新。

(1) AI 只理解，不定位

图例(1) 细节：locator 分层定位（阶段3/5 的展开）

拿到一个元素要定位时，从上往下试，命中唯一(count()==1) 才采用；找不到就降级/跳过，绝不蒙一个可能点错的。

元素 -> Tier1 精确匹配(快) ──命中唯一?──[run] [OK] 用

│            └─ label/placeholder/text   │
│            [!] Tier1 命中唯一后还要意图复验(方向(3)): 回读元素实际语义,
│               与 page_hint/semantic_name 比对(阈值0.15), 不符->降级下一策略

[pin] 本图例对应的设计要点

(2) locator 稳定性优先级

我们实现（Tier1 顺序）： data-testid > role+name > label > placeholder > text > CSS/路径（几乎不用）

为什么 data-testid 置顶？它是契约锚点——由团队约定保护"不随视觉/文案改版变"，确定性最强，是 locator 栈的主路径；自愈领域共识是让它当 Tier1，才能让自愈只在 <5% 的运行里触发。

那 role 为什么仍第一重要？它是用户语义层——可访问性对齐、开箱即用、无需被测应用埋点，是没有 data-testid 时的首选。

一句话：有 data-testid 用它（最稳）；没有就用 role+name（语义最稳）；CSS/路径永远最后（绑 DOM 结构，一改就断）。

(3) 防"假通过"

每个 locator 必须 count()==1 唯一命中。歧义->降级更稳；找不到->跳过；全败->报错，绝不蒙一个可能点错的。

(4) 同名元素靠"语义上下文"消歧

列表/表格/卡片里常出现同一 role+name 命中多个元素（如两个 checkbox、多个"删除"按钮），单靠 role+name 无法区分。probe 会给每个元素抓三类语义上下文：nearby_text（所属逻辑单元关键文本，如该项"写周报"）价值最高；container_heading（所在栏目标题）次之；help_text（aria-describedby/title 帮助文本）兜底。

定位时若 nearby_text 能锚定唯一父单元，就用 父单元含文本 -> 取 role 的过滤表达式唯一命中（如 page.locator("li").filter(has_text="写周报").get_by_role("checkbox")）；无上下文的裸元素诚实失败、绝不瞎选（防 false-heal 兜底）。

你在 cases/*.json 写自然语言用例（步骤用 op 操作类型 + desc 描述 + element 探测语义 + value 写死数据；断言用 asserts[] 数组，11 种 kind：文本 / 可见 / 隐藏 / 数量 / 属性 / 输入值 / URL / 勾选 / 未勾选 / 可用 / 禁用）。

动态占位符：数据里写 {datetime}/{date}/{uuid} -> 运行时解析固化（填表名==断言名，反复重跑不重名）。

用例级变量池 case.vars：存运行过程数据（新建合同名/系统返回编号/抓取字段值），供检查点断言 + 后续操作输入，function-scope 隔离。

并发用 pytest-xdist 多进程，每个 worker（会话）只起一个 Chromium 并全程复用（每条用例只新建 context+page，逐条 setup 0.57~0.66s -> 0.04~0.06s）；报告用 pytest-html 自动生成执行统计。运行：python -m framework.cli run --workers 2（cli 会先做资源预检，内存不够自动降并发）。

8新同学最容易踩的坑

这些坑都是真实踩过的，碰到先对应这里。

坑1 · 把 locator 字符串丢给 page.locator()

拿到的是一条 page.get_by_role(...) 这类的方法调用， 不能整串丢给 page.locator()——那会被当 CSS 解析，永远匹配 0 个。 正确做法：直接调真实方法拿 Locator 对象再 count() 校验。

坑2 · 让 AI 去"猜" selector

AI 一写就会吐出 #mui-4821、div:nth-child(3) 这种 一改版就废的脆弱玩意。要让它只引用 probe 探测出的语义小名。

坑3 · 忽视唯一性 = 埋下"假通过"

如果不清点命中了几个元素，点错了 Delete 还可能报绿——这是最危险的。 务必 count()==1 才放心用。

坑4 · 中文 placeholder / 中文字段

语义小名不要把中文干掉（否则全变成 el），保留中文才可读、 才和页面能对上。生成文件名也要处理中文，别挤成一片下划线。

坑5 · 被测应用的重启与端口

demo 用 http.server 时：要加 allow_reuse_address 避免 TIME_WAIT 卡端口；根路径要指到目标页，否则会列出目录、probe 抓到的全是文件链接。 （今天就跑通了这条路，没踩的注意。）

坑6 · 编码：别依赖「系统默认编码」（中文 Windows 上必崩）

实测事故：explore --ai（默认带 --verify）在中文 Windows 上报 UnicodeDecodeError: 'gbk' codec can't decode byte 0xbb in position 13 ——用例和脚本都生成了，偏偏校验这一步炸。根因：收子进程输出时写了 subprocess.run(..., capture_output=True, text=True) 却没指定 encoding， 于是父进程按系统默认编码（cp936/gbk）去解码子进程的 UTF-8 中文输出。
规矩：跨进程 / 落盘文本一律显式 UTF-8—— 收子进程输出用 framework.tools.common.text_io.run_capture()， 给子进程注入口径用 utf8_env()，本进程 stdio 用 force_stdio() （cli.main() 已经默认调了）。tests/特性9-质量闸门体系/test_utf8_io.py 会做 AST 全仓扫描， 再写出「靠默认编码」的写法直接测试失败。

问题结论
框架挑版本吗？ 不挑。实测 1.45 / 1.62 / 1.63 三版真跑均通过；用到的 API 全部落在 1.45 之前 （最「新」的是 2022 年的 get_by_role / get_by_test_id）； 代码零写死路径（靠 p.chromium.launch()，路径由 playwright 自己解析）
那为什么锁定？ 锁的是可复现，不是能力：不锁的话团队各装一个版本 -> 期望的浏览器 revision 各不相同 （实测 1.45->1124 · 1.62->1234 · 1.63->1243）-> 就会踩「包升级了、浏览器没重下」的坑。 锁定后大家的报错号、文档里的示例号永远对得上
锁死了还能升吗？ 能，升级是一次性、有意识的动作（三步规程见下），而不是各人机器上悄悄漂移
#  升级规程（三步走完再交付）

$ (2) python -m framework.cli setup --force-browser      # 按新版本重下浏览器
