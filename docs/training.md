# AI 混合 GUI 测试框架 · 新员工培训（V8.10.1）

> 与 `docs/training.html` 同源生成（`python build_tools/build_html.py`）· 2026-11-10

## 序 3 分钟看懂这是什么
*读完这一节，你应该能判断它适不适合你手头的事*

这套框架干的事一句话说完：用人话写一个场景，AI 把它排成步骤，框架用浏览器把步骤跑成可重复的用例——并且每一步都留证。

它不是「让 AI 自己开浏览器随便点」的黑盒工具。AI 只在两处参与：看懂页面有什么、把人话排成步骤；剩下的定位、点击、断言、取证、报告，全部是确定性代码在干。


### 0.1 适合谁 / 不适合谁

| 适合 | 不适合 |
|---|---|
| 要把**已有 Web 系统**的回归测试跑起来，且希望用例改起来比代码容易 | 第一次接触被测系统、连它有哪些页面都还不知道 |
| 系统界面常改，不想每次改版都改选择器（改了 AI 重排一次即可） | 只想要一个跑一次的爬虫 / 数据抓取脚本 |
| 需要在**内网无外网**的机器上跑（可离线回放） | 被测对象是 **iframe 内部**控件（当前未实现，见 1.6） |
| 要能说清「这条用例为什么过、为什么挂」—— 需要证据链 | 期望零配置、点一下就出结果 |


### 0.2 先记住这三条，其余都是细节

1. 主线只有一条命令：`python -m framework.cli all --ai --scenario-file <场景.yml>`。它把「识别 → 出用例 → 生成脚本 → 执行」一把跑完。注意：all 不含 explore 那一步的手工调用—— 它是内部按顺序跑 explore、generate、run 三段，你不需要（也不该）自己去敲中间那段。
2. 框架完全不懂你的业务系统：哪个页面、哪个字段必填、开票只能给已关闭订单——这些全部由你写在 `scenarios/` 里。框架只提供能力，业务事实归场景。
3. 断言不属于「操作步骤」：写用例时断言落在 `asserts[]` 而不是 `steps[]`。AI 能写的断言类型只有三种，且框架保证它写了就一定会执行（不然就是假绿）。

## 1 WHY · 为什么这样选型
*看懂这几条，后面所有设计都能自己推出来*


### 1.1 两条死路：为什么不能只用一种手段

做 GUI 自动化，只走极端走过两条路，两条都撞墙。这不是理论，是这类项目反复踩的坑：

| 做法 | 一开始很爽 | 最后为什么死掉 |
|---|---|---|
| **纯录制回放**（Selenium IDE / Playwright codegen） | 录一遍就有脚本，零门槛 | 界面一改选择器全废；录出来的脚本**没人敢改**；断言靠录制时那一下，业务规则根本录不进去 |
| **纯 AI 代驾**（让 Agent 自己看屏幕点） | 不用写任何东西，AI 自己探索 | 同一次输入**跑两次结果不同**（不可复现）；点错了还继续往下走（假绿）；每次执行都烧 token；出了事只有一段自然语言日志，没法取证 |
| **纯手写脚本** | 完全可控、跑得飞快 | 选择器写死；用例维护成本随页面数**线性上涨**；换个系统全部重写；写用例的人得会代码 |


### 1.2 所以选「混合」：各自只干自己最擅长的那一段

把「智能」与「确定」切开，一人一半，中间用一份可审的中间产物连接。这就是本框架的骨架，也是它被叫作「混合」的准确含义——四段闭环，浏览器在两端：

| 段 | 谁干 | 产出 | 为什么必须是它 |
|---|---|---|---|
| ① 看页面 | **浏览器**（探针） | 元素清单（语义名 + 定位信息 + 行/弹层信号） | 只有真浏览器知道页面上**此刻**有什么 |
| ② 排步骤 | **LLM 出编排**（`browser_use.llm` 直连，**非 Agent**） | 用例 JSON（自然语言步骤 + 语义名 + 断言） | 「人话 → 步骤」是语义活 |
| ③ 执行 | **确定性执行**（Playwright + harness） | 真实点击/输入 + 现场快照 + 录像 | 执行必须可复现：同输入同结果，才谈得上回归 |
| ④ 裁决 | **浏览器裁决**（断言 + 自愈 + 三态结论） | PASSED / FAILED（带原因）+ 证据包 | 过没过只能由被测系统的真实状态说了算 |

> **[注意]** 关于「AI 到底会不会自己开浏览器」——**不会，它没有浏览器的控制权**。全仓只 import `browser_use.llm`（LLM 客户端）做结构化直连编排，从未使用它的 Agent；`browser-use` 还是**可选依赖**，generate 与 run 两个阶段根本不需要它。


### 1.3 为什么是「两段物化」，而不是「边跑边问 AI」

如果每次执行都现场问 AI「下一步点哪」，会有三个躲不掉的问题：慢（每个动作一次往返）、不可复现（同场景两次可能给出不同步骤）、不可审（上线前你没法 review 一个还在生成的流程）。

所以 AI 只在 `explore` 阶段被调用一次，产出落盘成可读可 diff 的 `cases/*.json`；之后 `generate` 把它确定性翻译成脚本（这一步不调 AI），`run` 才真正执行。链路是：

```text
scenarios/*.yml  ──explore(AI)──>  cases/ai_*.json  ──generate(纯确定性)──>  scripts/generated/*.py
      人写的场景                AI 排的步骤（可审可 diff）           Playwright 脚本
                                          │
                                          └── run(pytest + harness) ──> log/latest/report.html + 现场证据
```

| 好处 | 具体体现 |
|---|---|
| **可审** | AI 排出来的用例是 JSON，人和 AI 都能看；不满意就改措辞重排，不用改代码 |
| **零 token 回归** | 日常回归只跑 `run`，一次 AI 调用都不发生 |
| **可回放** | AI 的原始回答录在 `output/llm_cassettes/`，无外网机器也能重现同样的步骤 |
| **失败可定位** | 挂了先看是「AI 排错步骤」还是「定位/断言执行出错」——两段边界清楚 |


### 1.4 一条铁律：AI 只做决定，框架只做执行

这条铁律落到代码上就是「同一件事只有一个入口」。新手最该知道的是这四个——因为它们决定了「我改了这个行为，会不会只改一半」：

| 能力 | 唯一入口 | 为什么必须收敛 |
|---|---|---|
| 目标地址改写 | `_rw(url, origin_name)`（回落 `_rewrite_base`） | 业务步骤、登录流、场景身份前置**三条导航**都必须走它 |
| 断言执行 | `_exec_assert()` | 主链路与登录链路共用；否则「AI 写了断言、登录段静默不跑」 |
| 动作词表 | `framework/shared/step_ops.py` | 同一个 `op` 在登录段与用例段必须同一套语义 |
| 行定位字段 | `ROW_LOCATOR_FIELDS` / `has_row_locator()` | 「第几行」只有一种表达（`row_index`） |


### 1.5 为什么要能离线回放 + 单包可跑

现实约束：客户内网没有外网、模型 key 不能带进去、团队里有人只想复现别人的失败。所以 AI 的原始回答会被录成文件，跟代码一起打进同一个交付包：

- 默认优先回放（有录像就不调模型，省 token 且结果稳定）；
- 录像不存在时才实时调用并录制，日志第一行会说明这轮走的是哪条；
- 回放不能当作「AI 行为正确」的证据 —— 它只证明「同一条链路的执行段能跑通」。

> **[禁止]** 判链路真伪只看日志第一行：`录像目录为空 -> 本次实时调用并录制` 才是真 AI；出现「复用已有录像」就是回放，此时 AI 根本没被调用。


### 1.6 诚实边界：这套东西现在做不到什么

| 做不到 | 现状与替代 |
|---|---|
| **iframe 内部**控件 | `feature_spec` 里标 **未实现**；这是如实标注的缺口 |
| **一个场景跨多个业务系统（不同 origin）** | **已支持**（V8.10.0）：`origins:` 起名 + 地址写 `${名字}/x.html`；`login.session.spread` 把会话铺到各 origin。仍做不到：**多套互不相通的登录体系**要拆多个场景 |
| AI 一次就把步骤排对 | 不能。它有概率排错，所以配了产出闸门 + 带原因重试 + 真跑校验 |
| 视觉兜底当主路径 | 只在确定性定位全失败时兜底，且点击后必须校验生效 |
| 没有断言也能判过 | 不会。没有断言的用例会被提示，但框架不会替你想断言 |

## 2 WHAT · 它由什么构成
*流水线 / 目录 / 数据链 / 11 块能力 / 六个关键实现*


### 2.1 四段流水线：每段的输入、产出、和「挂在这里长什么样」

| 段 | 谁 | 输入 | 产出 | 挂在这段的症状 | 耗时量级 |
|---|---|---|---|---|---|
| explore | AI | 场景 yml + 元素清单 | `cases/ai_*.json` · `element_maps/*.json` | AI 没排对 / 漏控件 | 1~4 分钟 |
| generate | 确定性 | `cases/*.json` | `scripts/generated/*.py` + datasets | 语义名对不上控件 | 1~3 秒 |
| run | 确定性 | `scripts/generated/` | `log/latest/report.html` + 现场证据 | 定位失败 / 断言不成立 | 单条 1~7 分钟 |
| verify | 确定性 | `cases/` 与实跑 | 两档校验结论 | 产出不合格 / 实测不过 | 同 run |

主线命令 `all --ai` 就是把上面四段（其中 verify 与 run 合并）按顺序跑完。开发期想省时间可以加 `--no-run`，停在 verify 为止。


### 2.2 目录结构：每个目录谁写、谁读、能不能删

| 目录 | 谁写的 | 谁读它 | 能删吗 | 进交付包 |
|---|---|---|---|---|
| `scenarios/` | 你（人） | explore | **不能**：唯一的人类输入 | 是 |
| `cases/` | AI（explore 落盘） | generate | 能：重跑 explore 会重新生成 | 是 |
| `scripts/generated/` | generate | pytest | 能：可再生成 | 是 |
| `scripts/datasets/` | generate | 生成的脚本 | 能：可再生成 | 是 |
| `output/element_maps/` | explore / probe | generate、run | 能：但会丢名字真值 | 是（只带最新 1 份） |
| `output/llm_cassettes/` | explore（录制） | 回放 | 能：但离线能力没了 | 是 |
| `output/verify/` | verify | 人看 | 能 | **否** |
| `log/` | run（pytest） | 人看 | 能 | **否** |

### 2.3 数据是怎么一路变成用例和报告的

记住四个文件形态就够了，其余都是它们的派生物：

| 形态 | 长相 | 关键点 |
|---|---|---|
| `scenarios/<模块>/<场景>.yml` | 人写的 YAML：页面、说明、前置动作、登录、业务数据 | 只写事实，不写运行时结论 |
| `output/element_maps/*.json` | 元素清单：每页控件（语义名 + 定位信息 + 信号） | 运行时名字的唯一来源 |

| `scripts/generated/*.py` | `generate` 翻译出的 pytest 脚本 | 别手改，下次 generate 会覆盖 |

### 特性 1 · AI 链路与离线回放
目标：只剩真 AI 链路（all --ai）与离线回放两种运行形态：都能跑通，且有一条统一验收入口
- **1.1 AI 链路与离线回放**：真 AI 链路（all --ai）与离线回放（录像）各自可独立跑通（不含已删除的手搓链路）
- **1.2 统一验收入口**：四条验收原则能用一条命令跑完（run_acceptance）。[!] 跳过策略（如 --skip-ai 必须显式留痕、SKIP != 通过）的判据物理住在 tests/特性9-质量闸门体系/，按「登记目录 == 物理目录」登记在 9.2
- **1.3 单包即离线可跑**：无外网机器解压交付包即可离线跑通 AI 链路（录像随代码包一起发，只有一个 zip）
- **1.4 目标地址覆盖对全链路生效**：`HYBRID_BASE_URL` 必须同时作用于**业务步骤、登录流、场景身份前置**三条导航路径（改写走唯一入口 `_rewrite_base`）；否则同一个包在用户内网/慢代理上会「一半打新地址、一半打写死地址」—— 会话 cookie 互不通用，第一个业务步就等不到元素。**跨 origin（V8.10.0）*

### 特性 2 · 语义识别与步骤编排
目标：把「人的自然语言」变成「可执行的步骤序列」—— 面向生成，对人友好也对机器友好
- **2.1 语义名生成与对齐**：AI 产出的语义名能落到真实控件上；宁可不映射（大声告警）也不许错映射（静默点错）
- **2.2 自然语言步骤编排**：场景 yml 的自然语言 → 步骤序列；步骤能直接声明定位方式（by+value）而不依赖探测清单；**AI 产出的有界重试口径**也归这里（产出侧被闸门拦下 -> 带原因重生成、上一轮缺陷记账不许留给下一轮；实跑档失败 -> 带原因整轮重来）—— 原登记在特性11，V8.6.3 按「登记目录 == 物理目录」改挂此处
- **2.3 步骤到定位的合成**：步骤里的语义名/属性如何合成可执行定位表达式（`verify_scope_locate.py` 物理住在 tests/特性3-分层定位与控件识别/，按「登记目录 == 物理目录」只挂 3.1）
- **2.4 场景声明契约**：人写的那部分：pages / pre / auth / data / probe_url —— 声明必须由场景提供，框架不懂具体系统
- **2.5 断言步骤可用性对齐**：**AI 能写的断言，框架都必须真的执行**：`ASSERT_OPS` 三个动作在登录链路与业务链路**走同一个执行入口**（`_exec_assert`），登录段不许再把断言丢掉；行断言失败时必须给出**该页实际列**（只说「没有这一列」等于让人重新猜）

### 特性 3 · 分层定位与控件识别
目标：在生产系统的复杂页面上仍能唯一定位到目标控件 —— 面向执行
- **3.1 顶层锚点加容器内下钻**：真实系统只有顶层元素有 testid；子元素靠「锚点 + 容器内相对语义路径」定位
- **3.2 多层嵌套容器**：容器套容器（区域内表格、表单里分组）时路径仍能唯一

### 2.5 六个关键实现（新手最该懂的）

这些不是「特性清单」，而是你排查问题时一定会撞上的六件事。每条给「它解决什么 → 现象 → 代码在哪」。


#### ① 分层定位：锚点 + 容器内相对语义

真实系统里通常只有顶层元素有稳定 testid，表格里每个格子都没有。所以定位不是「找一个全局唯一的元素」，而是「先找锚点容器，再在容器内按语义找」。代码在 `framework/features/f03_locate/`（`anchor_locate.py` / `scope_locate.py`）。

现象：日志里会看到 `行内定位（锚点+容器内相对语义）命中 N 个`。


#### ② 行定位 row_index：第几行只有一种表达

表格每行都有「数量」输入框，语义名完全一样。AI 必须额外给 `row_index`（正整数 = 第 N 行，从 1 起；`-1` = 最后一行，适合「刚新增的那行」）。探针还会给「区里现在唯一的输入类控件」打 `row_zone` 信号：只要有「新增行」这类动作，这个区必然会长多行——与当前行数无关。

> **[注意]** 「探测时唯一」不等于「运行时唯一」：探针看到 1 行、用例自己点「新增行」变 2 行，同一个控件就出现 2 个匹配。


#### ③ select 要等真选项，不能当帧判死

下拉框的 `<option>` 常常是异步填进去的：控件已经渲染，选项还没来。旧实现在当帧读不到选项就报错，慢机器/慢代理必挂。现在改成有界等待（`_wait_real_options()`），等不到仍然报错——绝不静默选第一个

现象：日志 `按「选第一项」选第 1 个真选项（共 13 个，跳过空占位）（等可选项就绪 63ms）`。


#### ④ 断言：唯一入口 + 失败必须给真值

三种断言（`expect_text` / `expect_url` / `expect_first_row`）都走 `_exec_assert()`。行断言写错列名时，报错会列出该页的真实列——只说「没有这一列」等于让人重新猜。实测收益：AI 读到真实列后能一轮自我修正。

现象：`表格没有第一行、或没有 'xxx' 列 —— 该页表格的实际列：[...]`。


#### ⑤ 自愈：点不中时先放宽、再报，不允许静默点错

定位失败时 `framework/features/f06_healer/healer_run.py` 会做一次「放宽阈值重试」（A 级）；仍失败则三态裁决（真 bug / 环境问题 / 用例问题）并落 `output/heals/` 的 json + md 供审 diff。自愈成功不算通过——它会留痕，但结论仍以断言为准。


#### ⑥ 质量闸门：宁漏不误伤

有两道闸：产出闸门（AI 给的步骤不合格 -> 带原因重试，不是静默放过）与打包体检（`build_tools/pack_release.py`：敏感词、行区控件缺 `row_index`、`VERSION` 与发行说明是否齐）。行区那条默认不拦，要拦得显式开 `HYBRID_ROW_ZONE_STRICT=1`——回放模式下硬拦会把主线命令挡死（2026-10-13 裁决）。

```bash
# 0) 建虚拟环境（Python 3.10+）
python -m venv .venv
.venv\Scripts\activate          # Windows
source .venv/bin/activate       # Linux / macOS

# 1) 装依赖
pip install -r requirements.txt          # 跑 run / generate 够用
pip install -r requirements-ai.txt       # 要跑真 AI 链路再装这个

# 2) 一条命令把剩下的事做完（装浏览器 + 自检）
python -m framework.cli setup
```

| 漏了什么 | 典型报错 | 怎么补 |
|---|---|---|
| 没装浏览器 | `Executable doesn't exist at .../ms-playwright/...` | `python -m framework.cli setup` |
| 没装 AI 依赖 | `ImportError: browser_use / openai` | `pip install -r requirements-ai.txt` |
| 没配模型 key | `[llm] 没找到可用的 LLM 凭据` | 在 `.env` 里配 `LLM_API_KEY` 等三项 |
| 没有图形界面（Linux 服务器） | 浏览器起不来 / 报 DISPLAY | 自动无头运行；想留证加 `--debug` |

> **[OK]** 模型只认 **OpenAI 兼容**端点，所以国内可用的 GLM / Kimi / 通义 / 豆包、本地 vLLM·Ollama 都能接，改的是三个环境变量而不是代码。

## 3.2 30 秒跑通自带 demo
*从零到 report.html，一条命令*

仓库自带一个订单系统的 demo（端口 `8000`），拿它练手最快。下面这条链路从零到出报告，一路都有东西可看：

```bash
# 1) 起被测应用（另开一个终端，别关）
python -m demo.app                       # 浏览器打开 http://localhost:8000 能看到登录页

# 2) 配好模型（只跑 run 的话这步可跳过）
#    .env: LLM_API_KEY / LLM_BASE_URL / LLM_MODEL

# 3) 主线一把跑完：识别 -> 出用例 -> 生成脚本 -> 执行出报告
python -m framework.cli all --ai --scenario-file scenarios/orders/orders_invoice_full_lifecycle.yml
```

每一步你该看到什么：

| 阶段 | 日志长这样 | 意味着 |
|---|---|---|
| 探针 | `[explore] 录像目录为空 -> 本次实时调用并录制` | 这轮是真 AI |
| 探针 | `[explore] 跨页探测: [开票页] ... -> 21 个控件` | 页面真被打开、控件被采到 |
| AI 出用例 | `[login] [OK] 登录步骤 4 步（AI 原始 4 步）` | 登录步骤落盘可审 |
| 生成 | `[1/2] generate 结束（耗时 1.8s）` | 确定性翻译，不调 AI |
| 执行 | `[TEST] [step 48] select: 期次号 …（等可选项就绪 63ms）` | 运行期真在点、真在等 |
| 结论 | `PASSED` / `1 passed in 397.14s` | 报告在 `log/latest/report.html` |

> **[注意]** 开发期不想跑执行段加 `--no-run`；只想重跑已有用例直接 `python -m framework.cli run`（零 AI 调用）。

## 3.3 命令速查：六个子命令
*先看这张表，再决定敲哪条*

六个子命令，日常只用得上前三个。区别在于「从哪一段开始、跑到哪一段停」：

| 命令 | 从哪开始 | 到哪结束 | 什么时候用 |
|---|---|---|---|
| `all --ai` | 场景 | 执行 + 报告 | **主线**：新写/改了场景，端到端验证 |
| `run` | 已生成的脚本 | 执行 + 报告 | 日常回归、改完框架自测（零 AI） |
| `verify` | 已有用例 | 产出校验 + 实跑 | 只想验「这批用例靠不靠谱」 |
| `generate` | 已有用例 JSON | 生成脚本 | 手改过用例，要重新翻译 |
| `prune` | — | 清理归档 | 磁盘涨了，按保留策略清 |
| `config` | — | 打印可调项 | 有哪些旋钮、当前值、从哪来 |

几个每天都在用的参数：

| 参数 | 作用 | 备注 |
|---|---|---|
| `--scenario-file <yml>` | 指定场景文件 | 最常用 |
| `--base-url` | 临时覆盖被测地址 | explore 不接这个参数 |
| `--no-verify` | 跳过试跑校验 | 快但结论弱 |
| `--no-run` | `all` 专用：停在 verify | 开发期省一半时间 |
| `--ai-retry N` | AI 产出不合格时重试次数 | 默认 2，上界 5 |
| `--debug` | 有屏弹浏览器 / 无屏录视频+逐步截图 | 并发强制降为 1 |
| `--case <case_id>` | 只跑一条用例 | 排查单条必备 |
| `--workers N` | 并发数 | 内存不够会自动降 |

全部参数（每个子命令一份）见附3；环境变量全表见附2。

## 3.5 scenario 怎么写
*这是你唯一需要动脑子写的东西*


### 3.5.1 放哪、怎么起名

场景文件住在 `scenarios/<模块>/<场景id>.yml`；文件名就是默认 id，要求小写蛇形（`^[a-z][a-z0-9_]*$`）。一个场景 = 一条端到端业务流，不是一条用例。


### 3.5.2 一个能跑的最小场景（照着改就行）

```yaml
id: todo_basic            # 可省：默认取文件名
scenario: |
  在待办页新增一条待办，标题写「今天要跑回归」，然后确认它出现在列表里。
target:
  url: http://localhost:8000/todo.html
  page: |
    待办页：顶部一个输入框 + 「新增」按钮，下面是列表（每行有标题和一个「完成」勾选框）。
login:
  url: /login.html
  scenario: 在登录页填写账号 super、密码 super@123，然后点「登录」
  wait: { url_not: login.html }
probe_pre: [切换为订单管理员]
probe_pre_host: 登录页
```

三个关键点：`scenario` 是人话（AI 读它排步骤）；`page` 是给 AI 的页面领域知识（哪个字段必填、哪个按钮会开弹层）；`wait` 必须是可观测条件——框架不允许用固定 sleep 判断登录成功。


### 3.5.3 字段全表

「给谁」一列很重要：AI = 会进提示词影响步骤编排；框架 = 只影响执行期行为（AI 看不到）；闸门 = 用来判定产出是否合格。

| 字段 | 必填 | 给谁 | 说明 / 写错的症状 |
|---|---|---|---|
| 字段 | 必填 | 给谁 | 说明 |
| `scenario` | **是** | AI | 自然语言动作流；空 = 加载期红 |
| `id` | 否 | 框架 | 默认取文件名；要求小写蛇形 |
| `tags` / `priority` / `owner` / `updated` | 否 | 人 | 归类与责任人 |
| `target.url` | **二选一** | 框架 | 单页入口地址；与 `pages` 互斥 |
| `target.page` | 否 | AI | 单页页面说明（领域知识） |
| `pages[]` | **二选一** | 框架+AI | 多页：`name` / `url` / `page` / `pre` / `probe_url` |
| `pages[].pre` | 否 | 框架 | 探测该页前要点的控件名 |
| `origins` | 跨 origin 时必填 | 框架 | `{order: http://host:8001, invoice: http://host:8002}`，页面地址写 `${order}/orders.html`；引用了未声明的名字 = 加载期红；不声明 = 单系统老行为 |
| `login` | 否 | 框架+AI | `url` / `scenario` / `wait`（`url|url_not|url_not_in|selector|text`）/ `session` |
| `login.session` | 跨 origin 时必填 | 框架 | `{token_from, param, store, key, spread: [order, invoice]}` —— 登录一次后把会话铺到各 origin；会话是 per-origin 的，不铺会被踢回**那个系统自己**的登录页 |
| `probe_pre` | 否 | 框架 | 探测期前置动作（写控件语义名） |
| `probe_pre_host` | 用到时必填 | 框架 | 前置在哪一页执行 |
| `business_context` | 否 | AI | 领域上下文 |
| `data[]` | 否 | 框架 | 数据驱动，一组 = 一条用例 |
| `assert_guard.must_contain` / `forbidden` | 否 | 闸门 | 产出用例必须/不许出现的关键词 |
| `auth` | 否（已淘汰） | 框架 | 接口登录老写法；新场景用 `login` |


### 3.5.4 七条纪律（每条都有对应的真实事故）

1. 写「能力」就要写「必要性」。只写「发票行（可新增行）」，AI 就会去点新增行——而页面其实已带入 1 行。多走一步的直接代价是一轮 717 秒的白跑。正确写法：「已自动带入 1 行，通常不需要点新增行」。
2. 只写事实，不写结论。别写「列表里共有 20 条」——那是运行时值，换个环境就错。
3. 断言的依据必须在页面上找得到。要断「第一行的合同编号是 HT-1001」，前提是该页真有「合同编号」列；否则 AI 写的断言永远不成立。
4. pre 只写控件名。它是「点一下」的清单（`编辑` / `新增行`），不是自然语言句子。
5. 页面说明是写给 AI 看的领域知识。它决定 AI 知不知道「必填」、「这个按钮会打开弹层」、「只能给已关闭订单开票」。
6. 一个页面一个 name，且页名要唯一。跨页同名控件会被自动改成 `原名@页名`；页名重名直接加载期红。
7. 别把口令写进场景。用 `password_env` 指向环境变量。

> **[OK]** 写完场景先只跑识别、不实跑：`python -m framework.cli explore --scenario-file <yml>`（加 `--ai` 才是真 AI，不加就是纯探针），确认控件采到了、页面对了再跑主线。

## 3.6 cases 怎么写
*AI 产的，但你要会读、会改、会挑错*


### 3.6.1 它从哪来、能不能改

用例住在 `cases/<场景id>/ai_*.json`，由 `explore --ai` 落盘。能读能改，但要知道两件事：

- `generate` 只读 `case_id` / `steps` / `asserts` —— 其余字段随便加，不影响执行；
- 场景一变（哪怕只改一句说明），用例里的 `scenario_fingerprint` 就不同步，判据会红并提示「重跑 explore 刷新用例」。不要手改指纹——那等于把「用例与场景同步」这件事做成假的。


### 3.6.2 顶层字段

| 字段 | 说明 |
|---|---|
| `case_id` | 用例 id（= 文件名去扩展名），`--case` 用它挑单条 |
| `name` | 用例名（进报告） |
| `base_url` | 生成期地址；执行期被 `HYBRID_BASE_URL` 覆盖 |
| `steps[]` | 操作步骤 |
| `asserts[]` | 断言——**断言不许写在 steps 里** |
| `scenario_id` / `source_scenario` | 溯源 |
| `scenario_fingerprint` | 场景指纹；不同步说明用例该刷新 |
| `pages` / `probe_pre` / `probe_pre_host` / `login` | 从场景继承的执行期声明 |
| `llm_source` | 哪个模型/哪份录像产出（审计用） |


### 3.6.3 steps[] 字段

| 字段 | 说明 |
|---|---|
| `order` | 步骤序号（从 1 起） |
| `op` | **动作** |
| `element` | 控件语义名（必须来自元素清单；跨页写成 `原名@页名`） |
| `value` | 填什么值；支持占位符 |
| `index` | `select` 专用：选第几项（从 0 起） |
| `row_index` | 行内控件：第几行（`-1` = 最后一行） |
| `by` / `value` | 属性直定位（css / testid / role） |
| `desc` | 人话说明，进日志与报告 |
| `requires_open` | 控件藏在入口后面，必须先点开 |


### 3.6.4 动作词表（唯一权威：`framework/shared/step_ops.py`）

操作类八个，都会改变页面状态（除 `goto` 外都必须落到真实控件上）：

| op | 语义 | 例子 |
|---|---|---|
| `goto` | 打开地址 | `{"op":"goto","value":"http://host/todo.html"}` |
| `click` | 点击（自动等可见可用） | `{"op":"click","element":"搜索@订单列表页"}` |
| `fill` | 输入框填值（先清空） | `{"op":"fill","element":"数量@开票页","value":"10","row_index":1}` |
| `select` | 下拉选一项 | `{"op":"select","element":"期次号","index":0}` |
| `check` | 勾选/取消勾选 | `{"op":"check","element":"选择订单_当前行"}` |
| `press_enter` | 回车 | `{"op":"press_enter","element":"订单名称@发票列表页"}` |
| `click_new_tab` | 点开新 tab 并切过去 | 跨 tab 流程 |
| `close_tab` | 关当前 tab 回上一个 | 跨 tab 流程收尾 |

断言类是另一套（不进 `steps[]`）：AI 只会写这三种，框架保证写了就执行；生成器另外还认 13 种 `kind`（手改用得上，见 3.6.5）。


### 3.6.5 asserts[] 字段

| 字段 | 说明 |
|---|---|
| `kind` | 断言类型；AI 只用 text / url / first_row，手改可用 13 种；未知 kind 直接失败 |
| `element` | 被断言的控件语义名 |
| `expect` | 期望值（text / count / attr / value / url / first_row 必填） |
| `row_field` | `first_row` 专用：验第一行的哪一列（必须是真实列名） |
| `after_step` | 跟在第几步之后（决定执行顺序） |
| `refresh` | `none` / `reload` / `research`（每轮重放最近一次搜索） |
| `timeout_ms` | 有界等待时长；缺省按场景声明推导 |
| `name` | `attr` 专用：属性名 |
| `desc` | 人话说明 |


### 3.6.6 六条硬规则

1. 断言不许写进 steps——`op` 里出现 `expect_` 开头的东西，说明结构放错了（步骤是「做」、断言是「验」）。
2. 不许写运行时才知道的值：发票号、共 N 条、当前时间戳。这些只能「反查稳定字段」（例：用合同编号 HT-1001 反查第一行）。
3. 行内控件必须给 `row_index`：给 `-1` 表示「刚新增的那行」，给正整数表示第几行。
4. 列名必须是该页真实列：`row_field` 写错时，框架会列出该页实际列供你改。
5. 一条用例一个业务闭环：别把「建单 + 开票 + 对账」塞进一条，挂了不知道断在哪。
6. 场景改了要重跑识别：指纹不同步会被判据抓住，这是有意的。

## 3.7 故障对照表
*按症状查，别从报错栈开始读*

这张表是「症状 → 先看哪里 → 怎么修」。左边那列是你在日志里能直接搜到的字符串。

| 日志里搜这个 | 说明 | 怎么处理 |
|---|---|---|
| 等可选项就绪 Nms | 下拉框选项异步填，已按有界等待拿到真选项 | 正常留痕。若报「等了 Nms 仍无可选选项」= 页面确实没数据或控件选错 |
| 行内定位命中 N 个 -> 按 row_index=-1 取行 | 行定位生效（-1 = 最后一行） | 正常。若报「命中 0 个」= 行锚文本对不上，去看该页实际行 |
| 重复控件 … 行定位缺失 | 有控件在多行重复，但用例没给行定位 | 回场景补说明，或重跑 explore 让 AI 重排 |
| 表格没有第一行、或没有 'xxx' 列 | 行断言写错列 / 页面还没数据 | 看报错里列出的「该页实际列」，改成真实列名；页面没数据就查上一步是否真的建成功 |
| 元素定位失败且自愈未成功 | 语义名与运行时 DOM 对不上（改版/未登录/在另一页） | 先确认「在正确的页、已登录」（回放/换地址时最容易踩），再看快照里有没有这个控件 |
| 登录步骤里有非操作动作，已跳过 | AI 想写的动作登录段不支持 | 现在是唯一的断言入口在跑，若仍出现说明动作类型不在 <code>ASSERT_OPS</code> 里 |
| 试跑预算 Ns（按声明等待推导） | 执行预算按场景声明的业务时长算出来 | 不用管；长期不够就调 <code>HYBRID_VERIFY_TIMEOUT</code> |
| 校验日志 …实测 FAILED | 某条用例真的没通过 | 打开它指的那个 verify 日志，找第一条 <code>E  </code> 行 |
| PASSED 但第 1 轮 FAILED、第 2 轮过 | AI 排错一轮后自我修正成功 | 算通过，但要回看第 1 轮报错——那是场景说明有歧义的信号 |
| [NG] 用例与场景不同步（指纹 …） | 场景改过，用例没刷新 | 重跑识别生成：把这条用例删掉再跑主线，别手改指纹 |

> **[注意]** 排查顺序：**先确认在正确的页、以正确的身份** → 再看控件在不在快照里 → 最后才怀疑定位算法。

## 4 交付与质量
*出门前的四条闭环*

这一段是「交出去之前必须做的」。四条闭环一句话：浏览器出证据 -> LLM 出编排 -> 确定性执行 -> 浏览器裁决，交付物只是这条闭环的一次快照，所以每次交付都要重新走一遍。


### 4.1 什么情况下不许出包

- 敏感词命中（雇主页/客户名/个人邮箱这类，对象级零残留）；
- 行区控件缺 `row_index` 且开了严格体检（`HYBRID_ROW_ZONE_STRICT=1`）；
- `VERSION` 与发行说明不一致，或包里缺最新发行说明；
- 包含 `output/verify` / `log/` 这类运行现场（它们会带凭据，永不外发）。


### 4.2 交付验证四步

| 步 | 做什么 | 怎么确认真的做了 |
|---|---|---|
| 步 | 做什么 | 怎么确认 |
| ① 产出自检 | 用例+脚本+元素清单齐不齐 | verify 产出档全绿 |
| ② 实跑 | 至少 1 条真跑过 | 日志里有 PASSED 与 N passed |
| ③ 打包体检 | `build_tools/pack_release.py` | 包内 VERSION / 发行说明 / 敏感词对账 |
| ④ 收件对账 | 发出去再核一遍 | sha256 逐字节比 + 无退信 |


### 4.3 新人交接清单（三页）

1. 自己跑一遍 3.2 的命令，直到看见 `log/latest/report.html`；
2. 读一条现成场景 + 它的用例，能把「场景第几句变成了用例第几步」对上；
3. 故意改坏一处（把场景里某页说明删掉），看框架怎么报错——比读十遍文档有用。
