## 一、② 意图复验阈值：口径写了两份（真隐患，不只是缺判据）

### 真值

```
locator_bridge_locate.py:50   INTENT_MIN_SIM = 0.15          ← 常量
locator_bridge_locate.py:221  if _sim(hint, blob) < 0.15 ...  ← 字面量，没引用常量
```

### 后果

**改常量只生效一半** —— 一处用新值、判定处还用旧值。这种「部分生效」最难查：
你调了阈值、以为全链路变了，实际只有一半路径变。

### 修法

判定处改引用 `INTENT_MIN_SIM`，并用**行为判据**钉住（不是只 assert 字符串）：

```python
monkeypatch INTENT_MIN_SIM = 0.15  -> 候选不降权
monkeypatch INTENT_MIN_SIM = 0.99  -> 同一候选被降权 0.20
```

**只有行为变了，才算常量真的被用上。**

### 边界值判据：裁定不做

`0.15/0.14`、`0.13/0.11` 这类边界值判据**标为可选**——查过：这两个值**没有 env / CLI 入口**，
只能改代码，触发频率太低，不值得单独排期。

## 二、③ `--debug` 两态：从「无判据」到「有判据」

### 这套逻辑本来就实现了

| 本机 | 应该发生什么 | 代码位置 |
|---|---|---|
| 有图形显示（Windows 桌面 / 带 X 的 Linux） | `HYBRID_HEADED=1` → **弹出 Chromium 窗口**，肉眼跟步 | 原 `cli.py:1481` 内联 |
| 没有（CI / 容器 / 无 DISPLAY） | `HYBRID_VIDEO=1` + `HYBRID_SHOTS=1` → **录制 webm + 每步一张 PNG** | 同上 |

### 问题在哪

**它内联在 `run()` 里十来行**，要测只能起真浏览器（二类），于是**从来没有自动化判据**。

而它守的恰恰是你定的那条纪律：

> **开关「开了就要好用」**：受限环境降级为等效可用（无 DISPLAY → 无头 + 录屏/截图），不报错退出

改坏的症状极其隐蔽：

> **Windows（有屏）上一切正常，无屏机器静默退化成没截图没录像** ——
> 等到要排查时才发现「什么都没留下」，而排查恰恰靠它们。

### 修法

把两态决策收敛成**纯函数**（唯一入口），`run()` 只负责应用结果：

```python
debug_env_plan(debug, has_display, *, workers, slowmo) -> {
    "env":    {"HYBRID_DEBUG": "1", "HYBRID_VIDEO": "1", "HYBRID_SHOTS": "1"},
    "lines":  ["调试模式：本机没有图形显示…", "→ 录下来给你看：视频 + 每一步截图 + trace", …],
    "workers": 1, "slowmo": 200,
}
```

判据用 **AST** 钉住：`HYBRID_HEADED / HYBRID_VIDEO / HYBRID_SHOTS` 的**赋值只许出现在唯一入口里**。
将来谁「顺手」在别处再写一行，当场红。

## 六、教训

1. **「同一口径写两份」比「没有判据」更该先修。** 没判据是「可能被别人改坏」，
   写两份是「现在就已经半坏」—— 只是症状要等有人改常量才显现。
2. **判据要钉行为，不要只钉字符串。** `assert "INTENT_MIN_SIM" in src` 挡不住
   「常量在、但没人用」。把常量改大再比对分数，才是真证据。
3. **测不了的代码等于没护栏。** `--debug` 两态内联在 `run()` 里十年也不会有人给它写判据；
   抽成纯函数后，5 条判据半小时写完。**先让它可测，才谈得上守护。**
