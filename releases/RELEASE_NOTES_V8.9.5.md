**日期**：2026-11-04
**主题**：`HYBRID_BASE_URL` 覆盖对登录/身份前置也生效 —— **交付到内网改 base 才真的能跑**

## 一、这次是 L22 取证时挖出来的，比 L22 本身严重

先看修之前的慢目标闸门（当前代码，2026-11-04 实测）：

```
[gate] 有界等待预算按延迟放大 3×：locate=15000ms ready=45000ms
[TEST] [step 6] goto: 打开【登录页】http://localhost:8000/login.html  (+18.5s)  [SLOW]
[TEST] [step 7] warn: primary 等了 15000ms 仍是 0 个 → 语义兜底 选择合同_HT_1001
RuntimeError: 元素定位失败且自愈未成功: 选择合同_HT_1001
[gate] 结果：Passed=0 Failed=2（共 2 条，80.6s）
```

**连第一个业务动作都没跑过去。** 历史台账把 L22 记成「订单详情页行内输入框等不到、应补行区就绪信号」——
**这个诊断对当前故障不成立。**

## 二、真正的根因：三条导航路径里只有一条认 `HYBRID_BASE_URL`

| 导航路径 | 修前 |
|---|---|
| 业务步骤 `_goto()` | ✅ 走 `HYBRID_BASE_URL` 改写 |
| **登录 `_login_flow()`** | ❌ **裸 `page.goto()`** → 仍打生成期的 `localhost:8000` |
| **场景身份前置**（fixture 里 `pg.goto(_host)`） | ❌ **同样绕过** |

后果一（跑不通）：两个 origin 的会话 cookie 互不通用 → 业务页未登录 → 「等了 15000ms 仍是 0 个」→ 自愈也救不回来。

后果二（更要命）：**交付包拿到内网、配 `HYBRID_BASE_URL` 指向用户系统时，登录会打到包里写死的地址。**
这条链路此前**根本跑不起来**，而慢目标闸门测的其实是「半套 8000 + 半套 8012 的混合物」。

> 身份前置那条更隐蔽：本机因为 8000 上还留着一个 demo，它**静默在错的身份下把整条用例跑完**；
> 我把那个 demo 关掉之后才立刻暴露成 `ERR_CONNECTION_REFUSED`。

## 三、修法：收口到唯一改写入口

```python
_rewrite_base(url)            # 新增：唯一的地址改写入口（只换 scheme/netloc，path/query 原样）
  ├─ _goto()                  # 业务步骤
  ├─ _login_flow()            # 登录两条路径（有 goto 步 / 靠 login_url）
  └─ 身份前置 fixture         # pg.goto(_rewrite_base(_host))
```

**行为验证**（fake page 抓真实导航 URL）：

```
HYBRID_BASE_URL=http://127.0.0.1:8012
  带 goto 步 -> ['http://127.0.0.1:8012/login.html']    ✅
  无 goto 步 -> ['http://127.0.0.1:8012/login.html']    ✅
未设 base      -> 'http://localhost:8000/login.html'   （原样，不凭空造 host）✅
```

## 四、修完 gate 又跑出第三处（也是就绪条件观测不到）

修完 ①② 后，gate 从「78 秒崩在 step 7」变成「**212 秒跑到 step 78**」，在新位置失败：

```
RuntimeError: 按行定位的 select 未给 value，且该控件没有任何可选选项（'期次号' 第 1 行）
```

300ms/请求时，`select` 控件已经渲染、`<option>` 还在异步填 → 旧实现**当帧就判死**。
快目标下同一步通过，看起来像「框架不支持行内 select」。

改为**有界等待可选项**：

```python
_wait_real_options(loc, deadline_ms=None) -> (真选项下标, 选项总数, 已等毫秒)
  · deadline 默认取 HYBRID_READY_TIMEOUT（慢目标闸门已按延迟放大到 45000ms）
  · 等不到 -> 返回空，由调用方**照旧报错**，绝不静默取第一个（不猜的红线不动）
  · 行内 select 与非行内 select **同一入口**
```

## 五、端到端真值：二类慢目标闸门**从红转绿**

| | 修前 | 修后 |
|---|---|---|
| 结果 | `1 failed, 1 error in 78.81s`（跑不到第一个业务步） | **`1 passed in 219.35s`** |
| 闸门结论 | `[NG] 慢目标下有用例失败 —— 回归了` | **`[OK] 慢目标下全绿（1 条）—— F1 就绪契约 + F2 有界等待 生效`** |

**L22（二类唯一红灯）关闭。**

## 六、判据（8 条，2 组负向自证）

| # | 判据 |
|---|---|
| 1 | 改写只换 origin，path/query（含 fragment）原样保留 |
| 2 | 未设 `HYBRID_BASE_URL` 时原样返回（不凭空造 host） |
| 3 | 登录流**两条路径**都被改写（行为） |
| 4 | 登录段源码不许出现未改写的裸 `page.goto` |
| 5 | **AST 扫 harness 全部 `.goto()` 调用点** —— 除 `_goto` 内 `page.goto(target)` 外都必须经 `_rewrite_base` |
| 6 | 选项异步到达时必须**等到**，不许当帧判死 |
| 7 | 等满 deadline 仍空 → 如实返回空、由调用方报错 |
| 8 | 两处 select 都走同一入口（不许一处硬判） |

负向自证：退回裸 `page.goto` → 判据 3/4 当场红；option 只读一次 → 判据 6 红。

> 判据 5 是这次最有价值的一条：**正是它抓出了「身份前置」那第二处** —— 逐个修容易漏下一个，
> 所以用 AST 覆盖全部导航点。

## 七、方法教训（写进 skill 了）

**「历史诊断」不能直接拿来当方案。** L22 的旧结论（补行区就绪信号）方向看起来对，
但当前故障根本不在那里 —— 它坏在**地址回写不全**，补行区就绪一分钱都治不了。

> 正确做法：先在**当前代码**上复现、读**真实报错**、跟到具体代码行，再谈修法。

另外一条工程习惯也再次验证：**有「第二个实例在跑」时，错的行为会静默通过** ——
身份前置那条就是被 8000 上残留的 demo 藏住的。取证时必须先清掉旁路实例。
