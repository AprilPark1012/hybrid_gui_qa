# 发行说明 · V8.4.1

**版本**：V8.4.1 ｜ **日期**：2026-10-09
**主题**：**修 Windows 实测暴露的 4 个 AI 编排缺陷**

> 一句话：**V8.4 让 AI 链路「跑得出、跑不对也报错」；V8.4.1 修的是「AI 产出里那些**看着对、换个环境就崩**的东西」。**

---

## 起因：内网 Windows 实测

按「**模拟用户本地环境**」的口径（重新起 demo → 删掉 `cases/ scripts/ output/` → 跑 `explore --ai`）在 Windows 上实测，**一轮跑出 4 个真问题**。

---

## P0-1 · AI 把表格行数据的具体值**写死**

**现象**（日志实录）：

```
 5. goto   -> http://localhost:8000/order_new.html?contract_no=HT-1001
 5. check  -> 选择合同_HT-1001
43. expect_text -> assert=HT-1001
```

场景原话是「选中**第一行**合同」，AI 却把它具体化成了 demo 里的**字面值**。

**⇒ 现在能跑通，只是因为当前 demo 第一行恰好是 `HT-1001`** —— 换一批数据、换个排序、换个环境，立刻崩，**而用例看着完全正常**。

**定性**：违反「**不许把观测到的具体值当地基**」（框架层零业务词、产出与数据解耦）。

**修法**（两层）：

| 层 | 做法 |
|---|---|
| **提示词硬约束**（根因） | 行数据一律走**声明式定位**：`row_text`（行锚）/ `expect_first_row`（首行断言）/ `cell_field`（按列取值）；跳转参数只能用场景 data 的 `{占位符}`；**字面编号一律不许出现在任何字段里**；例外：场景里逐字给出的可以照抄 |
| **生成后闸门**（兜底） | `reject_hardcoded_row_values()`，接 `_finalize_map()` 单点收口；**收集式**（不抛异常）—— 因为它是「换个环境就崩」的隐患，更适合**带原因让 AI 重生成**，而不是立刻判死 |

**判定实现的坑（判据抓出来的）**：第一版用 `\b` 词边界，而**中文是 `\w`** —— `选择合同_HT_1001` 里「同」与「H」之间**没有词边界** ⇒ **漏检**。改为「**前面不是 ASCII 字母**」。

## P0-2 · 语义校准只警告、不拦

**现象**：

```
118|  3. click -> 超@合同列表页 | 点击右上角头像打开角色切换菜单
114| [语义校准[!]] step3 「点击右上角头像打开角色切换菜单」 vs 控件语义 重叠度 0.00 -> 疑似选错
```

AI 选了控件 **`超`**（那是**登录后显示的用户名**）当角色菜单入口。框架自己的校准器**当场就报警了**，但它只设 `notes` + 打警告，**用例照样落盘** ⇒ 第 2 轮实跑崩在：

```
RuntimeError: 元素语义未找到: 超@合同列表页
```

**口径**：重叠度 **0.00** 不是「可能选错」，是「**一定选错**」。

**修法**：新增 `SEMANTIC_HARD_SIM = 0.02` 硬拦档位，严重误选收集进 `SEMANTIC_MISMATCH_NOTES` 供重试闭环。
**宁漏不误伤**：阈值贴着 0，只拦「完全不沾边」—— 正常步骤（「点搜索」vs 搜索按钮）放行（判据里有反向自证守着）。

## P1-3 · text 断言命中了**隐藏的 `<option>`**

**现象**：

```
TimeoutError: waiting for get_by_text("已关闭").first to be visible
  14 x locator resolved to hidden <option value="已关闭">已关闭</option>
```

用例本意是「等订单状态流转到**已关闭**」（状态在**表格行**里），但同页「已关闭」**也出现在筛选下拉的 `<option>` 里**（不可见）⇒ `get_by_text(...).first` 命中了那个 hidden option ⇒ 永远等不到 visible，白等 5s 超时（14 次重试全打在 `<option>` 上）。

**这不是用例写错** —— 是**框架的 text 断言没有排除不可见候选**。
真实系统里「同一个词既在下拉选项里、又在结果行里」**极其常见**（状态 / 类型 / 币种 …）。

**修法**：`_assert_text` **优先命中有可见性的候选**（逐个 `is_visible()`）；全不可见时退回第一个（**让断言如实失败，不掩盖问题**）。
落在 `_CONFTEST_TEMPLATE`（模板层）并**重生成 `scripts/generated/_harness.py`**。

## P2-4 · 上游不支持 `tool_choice`（能力差异，非抖动）

**现象**（每轮都出现一次）：

```
[explore] 第 1/3 次结构化输出失败 -> 结构化输出路径 ModelProviderError:
  Error code: 400 - {'error': {'message': 'Thinking mode does not support this tool_choice'}}
```

有重试兜底（第 2 次能成）⇒ 不致命。但代价：**① 白烧一次 LLM 调用；② 用户看到一行 `ModelProviderError` 红字，以为框架坏了。**

**口径**：这是**上游能力差异**，不是网络/服务抖动 —— **抖动该重试，能力缺失该记住并换路**。

**修法**：识别到「`tool_choice` / `thinking mode` 不支持」⇒ **本会话禁用结构化路径**、只走纯文本，日志降为 `[info]`。

## 如实登记：本轮**踩到的自己的两个坑**

| # | 坑 | 教训 |
|---|---|---|
| 1 | **批量替换误伤 70 个文件** | 我本想只换 GBK 编不了的 `⇒`（U+21D2），却把 `→`（U+2192，**GBK 本来能编**）一起换了。**批量替换前必须先实测「哪些字符真的编不了」** —— `⇒` 编不了、`→` 能编。 |
| 2 | **还原判断写错，把刚做好的修复一起还原了** | 我的「是否该还原」判断逻辑有误，`git checkout` 掉了 70 个文件（含 4 个修复）。所幸**新建判据文件是 untracked 没丢**，按记录完整重做并**重跑全部负向自证**。**教训：批量 git 操作前先备份工作区**。 |

## 给使用者：这版修完，同样场景应该看到什么

```bash
python -m framework.cli explore --ai --scenario-file scenarios/orders/orders_invoice_full_lifecycle.yml
```

| 以前 | 现在 |
|---|---|
| 产出里出现 `HT-1001` 字面编号 | 闸门挑出来、带原因让 AI 重生成（改用行锚 / 首行断言 / `{占位符}`）|
| `重叠度 0.00 -> 疑似选错` 只警告 | 判「严重误选」⇒ 带原因重试 |
| 断言死等 hidden `<option>` 超时 | 优先挑**可见**候选，不再白等 |
| 每轮一行 `ModelProviderError: tool_choice` | 识别一次后走纯文本，日志降为 `[info]` |
