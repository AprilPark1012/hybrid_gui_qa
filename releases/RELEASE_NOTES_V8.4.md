# 发行说明 · V8.4

**版本**：V8.4 ｜ **日期**：2026-10-09
**主题**：**让 AI 链路真正成为主推路径** —— 修掉 AI 编排的三个真实缺陷，并把「一次生成就对」换成「**校验 + 自动重试**」的工程闭环；同时把「常用可调项」从隐式环境变量变成可发现的 CLI 参数。

> 一句话：**V8.3.7 修的是「AI 链路跑不出产物」；V8.4 修的是「AI 链路跑出来也不可靠」。**

---

## 一、起因：干净环境 E2E 连续暴露三个真实缺陷

V8.3.7 交付后，按「**模拟用户本地环境**」的口径（删掉 `output/ scripts/ cases/` 后跑 `cli all`）反复实测，**每轮暴露一个不同的 AI 编排缺陷**：

| 轮次 | 现象 | 真因 |
|---|---|---|
| 第 1 轮 | AI 用例崩在第 1 步 | **AI 无视场景已声明的 `auth:` 登录前置**，自己编了一套登录流程，且**编造密码 `123456`**（场景文本里的真值是 `super@123`）⇒ 登录失败 ⇒ 停在登录页 ⇒ 后续断言等不到元素 |
| 第 2 轮 | `select 业务单元` 报 `did not find some options` | **AI 猜下拉选项的 `value`**（写 `value="1"`）；老版用例用 `index=0`（选第一项）是通过的 —— AI **看不到**选项的真实 value，只能猜 |
| 第 3 轮 | `generate` 崩在 `generator.py:684`，**一条脚本都没生成** | **框架自身缺陷**：`_add_payload_refs()` 只在 `value` 非空时设 `_payload_ref`，而渲染层对 `fill`/`select` **按下标取**它 —— 以前 AI 总塞个 value（哪怕是猜的）所以从未触发；约束生效后首次踩中 |
| 第 4 轮 | 质量闸拦下「假绿」 | **AI 拿 `index`（host 片段）当换页证据** —— 每个页面都含它，证明不了「确实换页了」 |
| 第 5 轮 | `explore exit=0` 但 `generate` 一条脚本都没出 | **框架的 `_act` 缺「select 没给值 = 选第一项」的能力**：旧实现落到 `select_option("")` -> 找 `value=""` 的选项 -> 30s 超时。AI 说的「选第一项」本来就是这个语义，**是框架没接住** |
| 第 6 轮 | 重试闭环连跑 3 轮 | 修完上面那条后，L1 实跑真正跑起来了；3 轮失败点暴露为「AI 断言页面上不存在的文字」等编排问题 —— **闭环在履职**，但过程中又暴露下面两个**我自己的实现缺陷** |

**⇒ 结论：用「提示词逐条堵」能堵住每一条，但堵不完** —— AI 编排是非确定性的。这才有了本版的正题。

## 二、特性 2「语义识别与步骤编排」：治 AI 幻觉 + 场景前置被无视

### 2.1 提示词硬约束：场景声明了登录前置 ⇒ 禁止生成登录步骤

`_build_planner_prompt(..., auth=...)` 新增 auth 感知：当场景 yml 声明了 `auth:`，提示词里加入**否定式硬约束**（不是「登录该怎么做」，而是「**不许做**」）：

```
【登录前置】（必须遵守，优先级高于上面所有通用规则）：
  · 本场景已声明登录前置，框架会在执行用例之前自动完成登录（含凭据与登录态）；
  · 因此你规划的步骤必须从登录之后的页面开始 —— 禁止生成任何登录步骤：
    不要 goto 登录页、不要填写账号/密码、不要点击登录按钮；
  · 也禁止在任何 value 里编造账号或密码 —— 真实凭据由场景持有，不属于你的规划范围。
```

**接线**：`cli.cmd_explore` -> `ai_explore(auth=…)` -> `_ai_explore_async` -> `_build_planner_prompt`
（`auth` 原本只用在跨页探测上，**没传给提示词** —— AI 因此根本不知道有登录前置）。

### 2.2 生成后闸门：AI 产出里夹带登录流程 ⇒ 拒绝落盘

新增 `_reject_login_steps()`，在 `_finalize_map()` 里**单点收口**（实测有 **3 处**调用：离线回放 / LLM 成功 / 兜底路径，放这一处才全覆盖 —— 与 V8.3.7「探测步骤收敛到唯一入口」同一个思路）。

判定口径（**宁漏不误伤**）：`goto` 目标 URL 带登录页特征，或操作的控件名是**登录专用短名**（账号/密码/用户名/登录名，长度 ≤4 —— 业务控件「账号名称」「客户账号」不会被误判）。

### 2.3 数据接地：不许编造业务数据

提示词新增【数据接地】小节：所有 value 只能取自提示里真实出现过的内容；**不许编造**账号、密码、编号、金额。

### 2.4 下拉选择约束：优先 `index`，不许猜选项 `value`

```
【下拉选择（select）的值从哪来】（必须遵守）：
  · 优先用 index：场景说「选第一项 / 第一行」时用 index=0，不要给 value ——
    你看不到选项的真实 value，猜一个必然失败；
  · 只有在场景/清单里逐字出现过该选项的可见文本时，才用 value 照抄那个文本；
  · 永远不要拿「看起来像编号的值」（1 / 001 / A1 …）去赌选项的 value。
```

## 三、特性 2 新增：**产出校验 + 自动重试**闭环（本版核心）

### 3.1 设计

**承认「一次生成就对」不可靠**，把**已有**的校验能力接成**有界重试**：

```
生成 -> L0 静态质量闸（毫秒级）-> 不合格？带原因重生成
     -> L1 实跑校验（几十秒）-> 不合格？带原因重生成
     -> 都通过 -> 落盘
```

**关键决策**（用户已审）：

| 决策 | 选择 | 理由 |
|---|---|---|
| 重试哪一级 | **两级都重试**，L0（便宜）先跑 | 便宜的先挡，省掉无用的浏览器实跑 |
| 原因怎么给 AI | 拼成「**上一轮你产出的用例被拦下了**」小节附到提示词 | 复用现有提示词机制，不新增接口 |
| 重试次数 | **默认 2**（`HYBRID_AI_RETRY` / `--ai-retry` 可调，`0` = 关闭） | 兼顾成功率与耗时/token |
| 防死循环 | 有界 + **同因不重试** | 原因没变说明再问也是同一答案，白烧 token |
| 录像回放模式 | **跳过重试** | 回放的是同一份录像，转 N 圈还是同一个坏产出 |
| 与质量闸关系 | **不弱化**，该拦仍拦、该 exit 仍 exit | 重试是「多给机会」，不是「放宽标准」 |
| 重试仍失败 | **如实报错 + 列出每轮原因** | 底线：宁报错，不放假绿 |

### 3.2 实现要点

- `_ai_retry_limit(env)`：默认 2，脏值**回落默认**（人手敲的环境变量不该让链路崩），**上界 5**（防手滑写 999 烧光 token）；
- `_should_retry_again(prev, new, attempt, limit)`：三条口径 —— 次数没用尽、本轮确实有失败原因、**原因与上一轮不同**；
- `_case_quality_reasons(e)`：把假绿红线的失败原因**文本化**（以前 `_report_case_quality` 直接 `raise SystemExit(2)`，想重试都没机会）；
- `_verify_cases_detailed(entries) -> (ok, reasons)`：实跑校验**同时给出给 AI 看的失败原因**（提取 `E ` 行 / `TimeoutError` / `not found`，**有界 40 行**）；
- L1 只能在外层：实跑要先 `generate`（要整轮产物齐了）⇒ 「生成所有 job -> verify -> 不合格整轮重生成」。

### 3.3 覆盖率

| 判据文件 | 条数 | 守护对象 |
|---|---|---|
| `test_ai_scenario_preconditions.py` | 10 | 提示词硬约束 + 登录闸门（含**负向自证**：摘掉约束必须红）|
| `test_ai_retry_loop.py` | 10 | 重试上限/同因不重试/原因进提示词/**接线**/回放跳过/闸门不弱化 |

**负向自证**（护栏判据必须能红）：
- 摘掉提示词的登录约束 ⇒ `test_prompt_forbids_login_steps_when_auth_declared` **红**；
- 摘掉闸门收口 ⇒ `test_ai_explore_calls_login_gate` **红**；
- 让闸门**无脑拦** ⇒ `test_login_step_gate_allows_normal_steps` **红**（证明「宁漏不误伤」口径成立）；
- 关掉重试 ⇒ `test_explore_has_retry_loop` **红**。

## 四、特性 5 新增子特性：**可选字段的渲染健壮性**

**事故**：AI 按新约束产出「`select` 只给 element、不给 value」后，`generate` 直接崩：

```
File "generator.py", line 684, in _render_pytest_case
    ref = st["_payload_ref"]
KeyError: '_payload_ref'
```

**根因**：`_add_payload_refs()` 只在 `if st.get("value"):` 为真时设 `_payload_ref`，而渲染层对 `fill`/`select` **直接按下标取** `st["_payload_ref"]` —— **假定这两个动作必带 value**。

**修法**：取不到 ref 就**不传 `value`**（`_act` 的 value 默认 `None`，正是「选第一项」该有的语义）。

**⇒ 这是「框架只适配了手搓用例」的又一个例证** —— 和 V8.3.7 那个「零产物」同一类病：**AI 的真实输出把隐含假设踩穿了。**

## 五、特性 10 新增：**常用可调项暴露为 CLI 参数** + `cli config`

### 5.1 起因（用户提问引出）

框架里有 **41 个 `HYBRID_*` 环境变量**，但：
- `.env.example` 里**一个都没有** ⇒ 用户**不知道它们存在**；
- 项目 `.env` **不入库、现状压根不存在**（`.gitignore:14`）⇒ 「设在那里」等于「每个使用者自己去猜、去建一个不在仓库里的文件」；
- shell 里 `export` 要会敲命令、且只在当次会话有效。

**⇒ 用户的判断（verbatim）**：「可以用CLI参数」。**不引入第二套配置文件** —— 否则与 env 并存会造出「双入口」，违背既定原则「**同一能力必须收敛成唯一入口**」。

### 5.2 新增 CLI 参数

| 参数 | 环境变量 | 适用子命令 |
|---|---|---|
| `--ai-retry N` | `HYBRID_AI_RETRY` | `explore` |
| `--shots` | `HYBRID_SHOTS` | `run` / `all` |
| `--video` | `HYBRID_VIDEO` | `run` / `all` |
| `--timeout S` | `HYBRID_CASE_TIMEOUT` | `run` / `all` |
| `--base-url URL` | `HYBRID_BASE_URL` | `probe` / `generate` / `run` / `all` |
| `--strict-locate` | `HYBRID_STRICT_LOCATE` | `run` / `all` |

**优先级**：**CLI 参数 > 环境变量 > 默认值**（在起任何子进程之前落到环境变量，生成物与 pytest 子进程天然可见）。

### 5.3 新增 `cli config` 命令

一屏列出**全部可调项**：`当前值 / 来源（CLI 或环境变量或默认）/ 一句话说明 / 对应的 CLI 参数`。

**刻意不列**框架运行期自设的变量（`HYBRID_RUN_ID` / `HYBRID_PARTITION` / `HYBRID_W` / `CASSETTE_STRICT` 等）—— 列出来只会让用户误以为该去调它。**判据 `test_internal_only_vars_have_no_cli_flag` 守着这条**。

### 5.4 判据

`test_tunables_exposed_as_flags.py`（**16 条**）：正向（每个用户可调项都有 CLI 参数、挂在正确子命令、`--ai-retry` 带值、映射表完整）+ **反面**（运行期自设变量不许开参数、一个环境变量不许映射两个参数）。

## 六点五、重试闭环自己的两个缺陷（被真实 E2E 逼出来的）

> 这两条特别值得记：**判据全绿的时候它们活得好好的** —— 只有真实 E2E 才逼得出来。

### 6.5.1 `generate` 失败不触发重试 ⇒ `exit=0` **假绿**（L1 设计漏洞）

**现象**：AI 有 4 个步骤**只写了 desc、没绑 element**：

```
step17 click（进入编辑态）没有 element
step20 click（提交整个订单）没有 element
step21 click（点底部返回回到订单列表）没有 element
step27 click（点击去开票跳转开票页）没有 element
```

`generate` 的**映射质量闸正确拦下**（拒绝产出垃圾脚本 —— 框架在正常履职），但 L1 报的是：

```
[!] 校验未执行：generate 失败（多半是「映射质量闸」拦下：目标没起 / 探测不可用）
```

⇒ **不算失败** ⇒ `explore exit=0` ⇒ **假绿**：`cases/` 里躺着 AI 产出，用户以为成功，实际**一条脚本都生成不出来**。

**修法**：**区分两类 `generate` 失败**

| 类型 | 识别 | 处理 | 理由 |
|---|---|---|---|
| **AI 产出不完整**（映射不上 / 没绑 element）| 命中「映射不上 / 没有 element」等 | `return False` + 失败原因 | **AI 能改** ⇒ 值得重试 |
| **环境问题**（目标没起 / 探测不可用）| 其他 | `return None` | **AI 改不了** ⇒ 重试白烧 token |

**口径**：**「产不出来」和「跑不过」一样，都是「产出不合格」。**

### 6.5.2 「同因不重试」被日志路径骗过 ⇒ 白烧一轮

**现象**：三轮实跑失败点**本质是同一个**（第 2、3 轮都是 `get_by_text("订单系统")` 幻觉），本该第 2 轮后就停，却跑到第 3 轮。

**根因**：失败原因文本里**必然**带每轮都不同的东西 —— 校验日志路径自带时间戳：

```
…/verify/ai_xxx_20261009_073944.log
…/verify/ai_xxx_20261009_074246.log
```

`prev.strip() == new.strip()` 逐字比较 ⇒ **永远判「不同因」** ⇒ 永远重试。

**修法**：新增 `_retry_reason_fingerprint()`，只抹掉**每轮必然变化**的部分（日志路径、时间戳、耗时、`/tmp/xxx` 临时目录），**不碰真正的失败描述**。

**负向自证**：把比较改回逐字 ⇒ `test_same_cause_detection_ignores_log_paths` **红**；同时另有一条判据守着「**不许把真差异抹平**」（两个不同失败点归一后仍须不等）—— 防修复做过头。

## 九、给使用者的话（怎么用新的东西）

```bash
# 1) 看有哪些旋钮可调（一屏可见，含当前值与来源）
python -m framework.cli config

# 2) AI 链路（主推路径）—— 产出不合格时会自动带原因重试 2 次
python -m framework.cli explore --ai --scenario-file scenarios/orders/orders_invoice_full_lifecycle.yml

# 3) 想多给 AI 几次机会，或临时关掉重试
python -m framework.cli explore --ai --scenario-file xxx.yml --ai-retry 4
python -m framework.cli explore --ai --scenario-file xxx.yml --ai-retry 0

# 4) 跑的时候想肉眼看 / 留证据
python -m framework.cli run --headed --slowmo 300 --shots
```
