## 一、起因：V8.9.2 那次「成功」是侥幸

V8.9.2 发给你后，你贴的 verify 日志里有这么一行（我要求你查的那条）：

```
[TEST] [step 82] select: 填写发票行：期次号选第一项  (+0.1s / 累计 160.7s)
```

**没有** `行内定位命中 N 个 -> 按 row_index 取行` → 说明 `期次号` 是**按唯一名直接命中**的
→ **运行期开票页当时只有 1 行**。

再查生成的用例 JSON：

```json
"op": "select",
"desc": "填写发票行：期次号选第一项",
"element": "期次号",
"index": 0                     ← 没有 row_index / row_text
```

**结论：AI 一步都没写行定位，那次通过是「页面正好一行」的运气**，不是修复生效。
（探针那次看到的是 3 行 —— 探测期与运行期的行数可以互不相同，两个方向都可能。）

## 二、根因：提示词的条件限定

V8.9.2 的措辞是：

> 凡是你排在某一步「新增行」之后要操作的，**必须**带 `row_index`

AI 的判断**完全正确**：开票页的行是**订单带入**的，用例里**没有**「新增行」动作
→ 按字面「不适用」→ 一步都不写。

**错在我的措辞**：我把「结构上必然多行」写成了「你的步骤造出多行」。

## 三、改法：无条件 + 给出「做了也没坏处」的取值

```
[!] 这些控件一律带行定位，不要因为「探测时只有一个」就省略。
    原因：这个区的行数是外部带入的（单据/订单明细），不一定由你的步骤产生 ——
    即使你的用例里从没点过「新增行」，运行期也可能已经有 2 行以上。
    做法：每一步引用这些控件都带 row_index ——
    · 已带入的原有行：写 1（或你要操作的第 N 行）；
    · 自己刚点「新增行」加出来的空行：写 -1（最后一行）；
    · 单行页面写 1 同样正确（唯一那行就是第 1 行），所以不要留空。
```

**关键设计点**：明确告诉 AI「单行页面写 `1` 也正确、不要留空」——
去掉了「省略更保险」的诱因，无论页面几行，写 `row_index=1` 都安全。

## 六、教训（写进 skill 了）

**条件限定的提示词在弱模型上不可靠** —— 它会按「最省事的分支」理解。

> 凡「必须做」的约束，写成 **无条件** + 给出「做了也没坏处」的取值，别给模型留判断空间。
