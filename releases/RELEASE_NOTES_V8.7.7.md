# V8.7.7 发布说明（2026-10-27）

> 上一版：V8.7.6（2026-10-27）· 版本号单一来源 = `build_tools/build_html.py:VERSION`

## 一句话

**61 步跑 3 分钟，没人知道时间花在哪。** 现在知道了：**73% 是业务等待，框架本身只占 27%**。
顺带发现框架假设了「被测应用能清库」—— 这个假设在生产环境不成立。

---

## 用户的问题

> 「60+ 步骤就要这么久，200+ 的话那不是更久？你看着有哪些地方可以提效的。」

在这个问题之前，有一件更基础的事没做：**日志里没有任何每步耗时**。
所以任何「优化」都只能是猜 —— 我确实猜过两轮，两轮都错了（见文末「过程记录」）。

## 第一步：先让耗时可见

在 `_log` 里量出「距上一步的间隔」+ 步骤序号 + 累计耗时：

```
[TEST] [step 62] click: 点击搜索  (+0.6s / 累计 13.5s)
[TEST] [step 63] click: 点开角色入口菜单  (+150.5s / 累计 163.9s)  [SLOW]
```

**为什么量在 `_log`**：它是**唯一的步骤日志入口**。改这一处就覆盖
`_act` / `_act_row` / `_assert_*` / `_goto` 全部路径 —— 分散埋点必然漏，而且口径会不一致。

单步 ≥5s 打 `[SLOW]`（本项目定位/断言的默认超时是 15s，5s 已属异常）。

## 实测结果（86 步全链路用例，本机真跑 205.92s）

| 项 | 耗时 | 占比 |
|---|---|---|
| **「等订单状态按时间流转到已关闭」** | **150.5s** | **73%** |
| 其余 85 步合计 | 55s | 27% |
| 平均每步 | **0.65s** | — |
| 最慢的正常步骤（点保存） | 1.5s | — |

**结论：框架本身一点都不慢。** 慢的是被测系统的状态流转 —— 那是场景里声明的有界等待
（上限 160s），框架只是老老实实在等。

## 那 200 步会更久吗

会，但是**线性的、而且很便宜**：

| 步数 | 纯执行耗时（0.65s/步） | 加上一次状态等待（~150s） |
|---|---|---|
| 61 步 | 40s | ~190s（实测 205s） |
| 100 步 | 65s | ~215s |
| **200 步** | **130s** | **~280s（4.7 分钟）** |

**真正决定总时长的是「有几次业务等待」，不是步数。** 一个 200 步但没有长等待的场景，
比 61 步带两次「等状态流转」的场景更快。

## 第二步：修掉会误导人的计时 bug

第一版埋点跑出来是这样的：

```
[TEST] [step 63] click: 点开角色入口菜单（切换角色按钮藏在该菜单里）  (+150.5s)  [SLOW]
```

看着像「点菜单死等 150 秒」。**但紧接着点菜单项只花了 0.4s** —— 菜单其实早就出现了。

**真相**：那 150.5 秒是夹在中间的 `[CHECK]` 断言（等状态流转），
而 `[CHECK]` 原来只 `print`、**不更新计时器**，于是耗时被算到了**下一条** `_log` 头上。

> **连我自己都据此误判了一次**，还写进回复里说是「点菜单死等」。

修法：新增 `_log_check()`，断言也计入 step 序号与耗时，两处 `[CHECK]` 打印点统一走它。
现在输出：

```
[CHECK] [step 70] v 断言: 有界等待：...最长约 160 秒...（已关闭）  (+149.3s / 累计 161.5s)  [SLOW]
```

**耗时归位，不再冤枉下一步。**

## 第三步：框架不该假设「被测应用能清库」

用户指出的问题（原话大意）：

> 真实生产环境不可能有数据 reset 开关，有些测试数据还是可以保留下来的，
> 咱们框架不能依赖这个 reset 的业务假设。

**原实现**：

```python
_RESET_URL = os.environ.get("HYBRID_RESET_URL", "http://localhost:8000/api/reset?purge=1")
```

两个问题：

1. **写死 demo 端点** —— 换到真实系统，每条用例前都白打一次不存在的地址；
   网络是黑洞（不是立刻拒绝）时，每次要等满 `timeout=5`。
2. **更根本** —— 框架在**假设**被测应用支持清库。生产环境没有这个开关，
   而且有些测试数据本来就该保留。

**新实现**：

| 取值 | 行为 |
|---|---|
| `off` / `""` / `0` / `none` / `no` / `false`（**默认**） | **完全不碰被测数据** —— 接真实系统的正确默认 |
| `auto` | 从 `TARGET_URL` / `HYBRID_BASE_URL` 推导 `{base}/api/reset?purge=1`（跑 demo 用这个） |
| 具体 URL | 原样使用 |

同时修掉一处缓存错误：原先 `HYBRID_RESET_URL` 在**模块加载时**被缓存进 `_RESET_RAW`，
之后改环境变量就不生效了（实测：设 `off` 仍返回 demo 地址）。现改为**每次调用现读** ——
可调项必须真的随时可调。

复位失败仍然**只告警、绝不中断用例**（真实系统没这个端点时也要能继续跑）。

### ⚠️ 行为变更（升级必看）

**`HYBRID_RESET_URL` 默认值从「demo 端点」变成了 `off`。**

- **跑 demo / 本地环境**：在 `.env` 里显式加 `HYBRID_RESET_URL=auto`，否则用例之间不再互相清理
- **接真实系统**：什么都不用配 —— 默认就不碰你的数据

## 判据（新增 18 条）

`tests/特性2-语义识别与步骤编排/test_step_timing_and_reset_default.py`

| 组 | 钉住什么 |
|---|---|
| 每步耗时 | 必须量「距上一步间隔」；必须用 `time.monotonic()`（不受系统时间调整影响）；必须打 step 序号 + 累计；慢步骤必须标 `[SLOW]`；必须 `flush=True` |
| **断言也计时** | `_log_check` 必须存在、必须更新计时器、必须占 step 序号、必须打自己的耗时；**不许再有只 print 不计时的 `[CHECK]`**（钉死那次误判） |
| 唯一入口 | `_LOG_LAST` / `_LOG_T0` 只允许在 `_log` 与 `_log_check` 各更新一处，不许散落 |
| reset 默认 | 不设变量时必须**什么都不做**；六种 off 写法都认（大小写不敏感） |
| reset auto | 从 `TARGET_URL` 推导；末尾斜杠要处理干净（不能拼出 `//api`） |
| **不许缓存** | 源码里不许出现 `_RESET_RAW`；函数体内必须现读 `os.environ` |
| reset 容错 | 失败只告警、仍 `yield`（不中断用例） |

## 过程记录（两轮误判，如实留档）

1. **误判一：试跑跑在「脏数据」上。**
   依据是 `verify 397.3s` vs `run 201.4s`（同脚本同断言）。我据此提出「让 verify 也 reset」。
   **用户当场否掉**：他每次跑前都删了 `demo/.data`，且 explore 探测只点击不提交、不写数据。
   我查代码确认了 —— `run_pre_actions` 确实只做 `_resolve()` + 点击，没有任何提交。
   **教训：先有数据再解释，不能从「两个数字不相等」倒推出一个因果故事。**

2. **误判二：「点开角色菜单死等 150 秒」。**
   第一版埋点把断言耗时算到了下一步头上，我直接把日志读成「点击慢」。
   **框架其实没死等，它按场景声明的 160s 上限在等订单状态流转。**
   **教训：埋点本身也要被验证** —— 耗时归属一错，指的方向就完全相反。

3. **真正有说服力的顺序**：先加埋点 → 跑一次 → 看数据 → 再下结论。
   这版做完之后，「397 vs 201」的谜也就不攻自破：**两边等的是同一个业务状态，波动区间 150~350s。**
