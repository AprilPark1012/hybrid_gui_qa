# V8.7.2 发行说明（2026-10-25）

> 承接 **V8.7.1**（2026-10-21）。本版只做一件事：**让「失败 → 修复」这个闭环可以在离线环境复演。**
> 属于**契约变更**（回放不再一刀切跳过重试），涉及 2 条既有判据 + 特性规格。

---

## 一、问题（真机实测，不是推演）

在 Windows 本地按主推链路跑 `orders_invoice_full_lifecycle`：

| 轮次 | 结果 | 真因 |
|---|---|---|
| 第 1 轮（实时 AI） | **FAILED** | AI 想不到「两步保存」，整单没提交 → 订单状态不流转 |
| 第 2 轮（带失败原因重生成） | **PASSED** | 用例里补上「两步保存之②」，并补了行定位 |

失败原文：
```
AssertionError: 等待超时：160000ms 内表格第一行的 'orderStatus' 始终不含 '已关闭'
（轮询 153 轮 · refresh=research · 最后读到 ' 已新建'）
```

⇒ 修复确实来自**重试轮**。录制时三轮 AI 回答都落进了 `output/llm_cassettes/`。

**但换到回放模式就复现不了这段**：

- 严格键命中的是**第 1 轮那份**（有缺陷版）→ 必然复现同一失败；
- 第 2 轮那份录像（成功版）的 prompt **含失败原因**（`轮询 153 轮` 这类运行时数值，回放时是 `162` 轮）
  → `sha256(prompt)` 必然不同 → 严格键永远不中；
- 而旧实现在 replay 下**一刀切放弃重试**，所以第 2 轮那份录像**永远用不上**。

---

## 二、根因

`cli.py` 两处 replay 分支：

```python
# 产出档（L0 校验不合格）
if replay:
    print("录像回放模式：重试无意义（回放的是同一份录像）-> 直接汇报")
    break                                   # ← 停下产出重试循环

# 实跑档（L1 实跑失败）
if replay:
    print("录像回放模式：重试无意义（回放的是同一份录像）-> 直接汇报")
    raise SystemExit(3)                     # ← 整体退出
```

它依据的前提是「**回放的是同一份录像，转 N 圈还是同一个坏产出**」。
**这个前提不成立**：重试会把本轮失败原因写进 `feedback`（`_next_round_feedback`），
**下一轮 prompt 就是新的**；录像若录了那一轮，就该继续推进。

---

## 三、修复

1. **两档都放行回放重试** —— 仍受 `_should_retry_again` 有界约束（次数上限 + 同因不重试），
   不是无条件重试。
2. **`CassetteError` 一并接住** —— 这是放行重试后才暴露的隐患：
   第二轮缺录像时会从重试路径抛出 `CassetteError`，而它与 `AiExploreError` 是**兄弟类不是父子**，
   原先只在 cassette 构造阶段被捕获 → 会变成**未捕获 traceback**。
   现在 exit 2，并明确报「**回放缺这一轮的录像 / 录像包不完整，请用 `--llm-record` 重录完整包**」。

**旧判据要防的「白转 N 圈」没有放松**，改由两件事覆盖：
- 有界重试（`_should_retry_again`）；
- 缺录像 **fail loud**（exit 2，根本不进第二圈）。

## 七、对使用者的影响

- **非回放模式（`--llm-record` / 默认实时）**：行为不变。
- **回放模式（`--llm-cassette`）**：遇到校验失败/实跑失败时**不再当场放弃**，
  而是带着失败原因去录像目录找下一轮的录像：
  - 找到了 → 继续推进（这是本版要的能力）；
  - 找不到 → `exit 2` + 明确报缺（**不会**静默降级、**不会**抛 traceback）。
- **录像包要求变高**：想让「失败→修复」可离线复演，录像里必须包含**重试轮那一份**。
  录制时正常经历失败→修复即可自然录到；只录一轮的包在旧实现下能放通（因为当场就停了），
  在新实现下会走重试轮那一查，缺就报缺。
