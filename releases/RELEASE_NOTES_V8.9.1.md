# V8.9.1 发布说明

**发布日期**：2026-11-02
**主题**：把「查不下去的失败」改成「一眼能指认」—— 回放选了旧录像、重试是死路、超时不留现场、慢目标被误判卡死、慢轮刷屏淹没信号

---

## 一、这一版解决什么问题

用户实测报了两种故障：**离线回放失败**（0 产物）与**试跑 900s 被判卡住**。逐个复现后一共揪出 **5 个**问题，
它们有个共同点：**错了不告诉你错在哪**。

---

## 二、五个缺陷与修法

### 1) 回放选错录像（回放失败的真因）

录像查找第三级「相似度匹配」写的是 `r > best[0]` —— **平手不换**。同一场景先后录过两份
（前一份的答案后来被闸门判不合格、后一份才对），两份场景相似度都是 100%，于是永远拿到
字典序先扫到的 = **更旧、已被判死的那份** → 闸门拦下 → 重试还是它 → 死路。

结构键那一级 2026-10-11 就修过「同键多份取最新录制」，**这一级漏了同一口径**。

**修法**：平手按 `created_at` 取最新（与结构键完全同一口径）；提示措辞从自相矛盾的
「相似度 100.00%；不是逐字相同」改成「**场景相似度 100.00%**」（100% 的含义就是只差时间戳/计数这类动态值）。

**实测前后对比**：

| | 命中录像 | 里面是什么 | 结果 |
|---|---|---|---|
| 修前 | `4466a560…`（14:07:33） | `expect='orders'`（已被判假绿那份） | L0 拦下 → 重试用尽 → **0 产物** |
| 修后 | `94ce5d9a…`（14:20:19） | 正确答案 | 50 步用例 → **试跑 PASSED 405.2s** |

### 2) 回放模式下的「重试」是死路

录像决定内容，重试不产生新答案。

- **L1 档**：两轮拿到**同名同内容**的用例，第二轮必然重复同一个失败，白等一个 900s 试跑窗（两轮半小时）。
- **L0 档**：重试的 prompt 虽带失败原因，但录像里没有那一轮时会**回落到相似度**并命中同一份 →
  转两圈后只报「重试用尽」，用户看不出「录像里根本没有第二个答案」。

**修法**：两档都在**动手之前**用「答案出处（`llm_source` / 录像 key）」判定同源并立即停，
明确给出三条出路（`--llm-record` / 重录含重试轮的包 / 先修场景断言）。

### 3) 试跑超时什么都不留

`TimeoutExpired` 里**本就捕获着**子进程的全部输出（含 `[step N]`），原实现直接丢掉 —— 用户只看到一句
「真卡住」。**修法**：打出「**停在**：[step N] …」+ 全文落盘 `output/verify/<case>_TIMEOUT_<ts>.log`；
抓不到步骤输出就明说「卡在**用例开始之前**」；有 `watchdog.txt` 就贴栈尾，没有就明说「看门狗没装上＝卡在夹具之前」。

### 4) 只杀直接子进程

`subprocess.run(timeout=)` 杀掉 pytest 后，它拉起的 **Chromium 可能还活着**、还占着被测服务 →
重试轮在更脏的环境里跑 → **两轮都超时**。**修法**：新增 `run_capture_tree()`，
POSIX 用 `killpg`、Windows 用 `taskkill /F /T`，连树杀，并把已捕获输出随异常带回。

### 5) 慢目标被误判成「卡死」

试跑预算原来写死 900s（按 62 步基线 360s 的 2.5 倍）。但真实用例里「等订单状态自动流转」这类
**有界等待**是按场景声明设的（实测 4 处 × 160s）。慢机器上一处都没命中时：

```
正常执行 400~500s + 4×160s ≈ 1040s > 900s   ← 用例在「正常地等」，却被判「真卡住」
```

**修法**：预算按**生成脚本里真实的 `timeout_ms=`** 推导（基线 600s + 声明等待 × 1.2，本例 **1368s**），
开跑前把依据打出来；**用户显式设了 `HYBRID_VERIFY_TIMEOUT` 就听用户的**，框架不覆盖。

### 6) 轮询太粗 + 慢轮刷屏

「重放最近一次搜索」是**每轮都做**的动作，慢目标下一次可能吃掉几十秒 → 160s 的业务等待只够轮询
**3 轮**，而业务值约 150s 才变，正好卡临界（第 1 轮红、第 2 轮才绿，白烧一轮生成 + 一轮试跑）。

**修法**：该动作走 **2 秒快速窗口**（`_FAST_WINDOW_MS`，只夹等待上限、不改「探到就走」的语义，
用完**自己还原**）。实测同一等待能轮询 **148 轮**。

同时把慢轮日志做成**两级**：

| 级别 | 口径 |
|---|---|
| 个体 | 只在单轮 **≥ 5 秒**时逐条打，且**最多 3 条** |
| 汇总 | 退出时**一条**：`有界等待汇总：共 148 轮 · 慢轮 0 个（单轮>=5s） · 最慢 1.1s（第 120 轮）· refresh=research` |

> 这条是自己踩完自己修的：第一版阈值定 1.0s，健康机器每轮约 1.09s（含 500ms 固定间隔），
> 一次等待打了 **243 行**，把信号全埋了。

## 三、验证真值

| 项 | 结果 |
|---|---|
| 一类框架自测 | **1573 passed / 3 skipped** |
| 回放链路（修前） | L0 拦下 → 重试用尽 → **0 产物** |
| 回放链路（修后） | 命中正确录像 → 50 步用例 → **PASSED 405.2s** |
| 慢目标配置端到端（`HYBRID_LOCATE_TIMEOUT=15000`） | **PASSED 405.3s**，预算按声明推导 **1368s** |
| 有界等待轮询密度 | 修前 3 轮 / 160s；修后 **148 轮 / 150s** |
| 日志干净度 | 修前 **243 行**刷屏；修后 **0 条**个体告警 + 8 条汇总，用例日志 193 行 |
| 新判据 | **17 条**（试跑超时留现场 12 条 + 有界等待每轮成本 5 条） |
| 负向自证 | 摘掉「取最新」/ 摘掉「夹子」→ 判据当场红 → 还原绿 |

另改 3 条旧判据：原先用「字符窗口」找报错里的关键信息，加了诊断内容后命令被挤出窗口 → 假红；
改成「切到整段 `except` 体、钉必须包含哪些信息」—— **判据钉契约，不钉排版**。

## 四、诚实边界

1. **Windows 上「每轮 53 秒」的确切成因尚未完全定位**。Linux 健康页面实测每轮 0.45~1.1s，复现不出。
   新日志会自己把每轮耗时打出来（`共 N 轮 · 慢轮 M 个 · 最慢 X.Xs`），下次直接指认是定位、
   就绪等待还是页面响应。
2. **L22（慢目标下行区就绪信号缺失）仍未修** —— `verify_slow_target` 依旧是二类里唯一红灯。
3. **取证（CDP 证据包）与视觉 grounding 兜底**仍是「可调用、已实测」，**尚未在 run 失败路径上自动触发**。

---

## 五、升级注意

- 新增/变更可调项：`HYBRID_VERIFY_TIMEOUT` 语义变了 —— 现在它是**默认预算**，实际预算会按用例声明的
  业务等待**上调**；**你显式设了它就以你为准**（框架不再推导）。
- 有界等待的动作走 2 秒快速窗口，`HYBRID_LOCATE_TIMEOUT` 不再作用于「重放搜索」这一步。
- 慢轮日志阈值 5 秒、个体最多 3 条，避免刷屏。
