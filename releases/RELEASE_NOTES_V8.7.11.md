## 一、R8 修订：3 方 → 4 方

**原来**：`README / docs/training.html / 代码` 三者以代码为基准同步。

**现在**：基准只有一个 —— **`framework/` + `demo/`**（行为、默认值、命令、参数、报错口径的唯一真值）。

| 方 | 位置 | 角色 | 漂移风险 |
|---|---|---|---|
| ① 基准 | `framework/`、`demo/` | **唯一真值** | — |
| ② `cli --help` | `cmd_*` docstring + `FLAG_SPECS`/`CMD_FLAGS` | 自动投影（改 docstring 即改 help） | **低** |
| ③ `README.md` | 仓库根（250 行硬预算） | 人工投影 | **高** |
| ④ `docs/training.html` | 源头是 `build_tools/build_html.py` 的**模板正文** | 生成物 | **高** |

## 二、你的提议（把 build_tools 排除出基准）—— **合理，但要拆三类**

我查了 `build_tools/` 的构成：`build_html.py` 一个文件 **437KB / 5057 行，占整个 build_tools 的 81%**，其余 8 个都是 4~35KB 的小工具。所以问题基本全在它身上。

而它里面混着**三种性质完全不同**的东西：

| 类 | 具体是什么 | 是否以 `framework/` 为基准 |
|---|---|---|
| **① 它自己就是基准** | `build_html.py` 的 `VERSION`（版本号单一来源）、`CHANGELOG`（冻结历史） | ❌ 不能 —— 否则循环（README 的版本要跟它对） |
| **② 它是投影** | `build_html.py` 的**模板正文**（讲框架怎么做事、开关默认值、命令用法） | ✅ **必须跟 `framework/` 走** |
| **③ 它是工具** | `check_cassettes.py`、`measure_explore_prompt.py`、`migrate_element_map_keys.py` 等 | 与框架行为无关，不在同步范围 |

**你说的坑就在 ②** —— V8.7.10 那轮就是这么踩的：`framework/` 把 `HYBRID_RESET_URL` 默认值改成 `off`，但 `build_html.py` 的模板还写着 `localhost:8000/api/reset?purge=1`，于是**培训页讲旧话**。

**模板就是培训页的源头，它不跟 `framework/` 走，培训页必然漂。**

## 三、一个反直觉的发现：`cli --help` 是最不容易漂的

依赖关系的真实形态：

```
【唯一基准】 framework/ + demo/
                 │
     ┌───────────┼────────────────────────────┐
     ▼           ▼                            ▼
 投影A          投影B                        投影C
 build_html.py  README.md                   cli.py 的 cmd_* docstring
 的【模板正文】                              │（自动拼装）
     │(渲染)                                  ▼
     ▼                                    cli --help
 docs/training.html

【版本事实·自成来源】build_tools/build_html.py 的 VERSION + CHANGELOG
   ← README / training.html / RELEASE_NOTES 的版本号都向它看齐
```

**`cli --help` 的源头就是 `framework/` 里的代码**（`cmd_*` 的 docstring），改代码时顺手就改了 —— 所以它几乎不会「忘记同步」。

**真正的漂移高发区是 README 和 `build_html` 模板**，因为它们是**人工维护的第二份文字**。

**今天查出的 3 处过时，100% 都在这两处**；`cli --help` 只有一处，而且不是「忘记同步」，是**当初就写错了**（`--case contracts_search_by_no`，那个 case 从来不存在）。

**结论**：判据该往 README 和模板上加力。

## 四、六条操作规则（每条都有实测实例）

1. **示例命令不写死具体值** —— 真实 case id 带时间戳、每次生成都变，写死任何具体 id 都注定过时。用 `<case_id>` + 说明来源。
2. **数字必须机器数** —— `1218 passed` 实为 `1337`；「45 项」实为 **51 项**。
3. **全文扫，不止改参数表** —— 参数默认值改对了 ≠ 正文对了。漏掉的 3 处是**陈述框架行为**（「每条用例开始前框架会复位数据」），那比参数写错更危险：新人据此写跨用例依赖，demo 上碰巧过，**接真实系统必翻车**。
4. **冻结区靠偏移定位，不靠印象** —— `build_html.py:2161-2166` 曾被我当成正文要改，机器算偏移才确认在 CHANGELOG 冻结区内。**改错历史比漏改更糟。**
5. **同一件事不维护第二份** —— 可调项清单只有 `cli config`；主线入口只有 `all`（`--no-run` 开在 `all` 上，不另开 `explore --ai` 当第二条主线 —— 被判据 `test_j2` 判红过）。
6. **改完重渲 + 跑全量** —— 顺序固定：改代码 → 重渲 → 跑全量 → 看绿。

## 六、新判据：`test_no_hardcoded_case_id.py`

**守什么**：`--case` 示例里写死的 case id 必须真实存在，且**不许带时间戳**。

**边界（宁漏不误伤）**：

| 情况 | 判定 |
|---|---|
| 写死的值**不存在**（`contracts_search_by_no`） | **红** —— 读者照敲就报错 |
| 写死的值**带时间戳**（`style_161243`） | **红** —— 下次生成就变 |
| 写死的值存在且稳定 | 不红 |
| `<case_id>` / `…` / 单字母 `a`（语法说明）/ 中文说明 | **放过** |

**+ 正向自证**：必须有至少一处 `--case <case_id>` 式说明 —— 否则「把示例全删了」也能过第一条判据，那是把能力藏起来，不是修好。

**反向验证做过**：把 `contracts_search_by_no` 塞回 `cli.py` → 判据立刻变红；还原 → 2 passed。

**开写时也踩了两个误伤**（都记了）：
- `--case 可重复；case_id = …` 里的中文被当成 id → 只认 ASCII 标识符形态
- `--case a --case b`（语法说明里的单字母）→ 单字母算占位符

## 七、R10 补充：交付件还有录像（你 2026-10-28 指出）

**你的原话**：「R10，场景变了，交付件不仅仅是 cases/ scripts/ 需要刷新，还有录像 output/llm_cassettes 也要刷新的」。

**核对结果：你说得对，(1) 的三条触发源表里「要重做什么」那栏确实漏了录像。**

| 触发源 | 改前「要重做什么」 | 改后 |
|---|---|---|
| ① 场景变了 | 用例 + 脚本 | **录像 + 用例 + 脚本**（三样都刷） |
| ② 用例变了 | 只重做脚本 | 只重做脚本，**录像不动**（录像只覆盖语义识别那一步） |
| ③ demo / 页面变了 | 场景核对 + 用例 + 脚本 | **录像重录** + 场景核对 + 用例 + 脚本 |

**为什么这一栏漏了很危险**：`(2.4)` 那节虽然单独讲了"4+2 重录口径"，但读者先看的是 (1) 汇总表 —— 看到「场景变了 ⇒ 重做用例+脚本」就以为完事了，**用例会建在过期录像的语义上**，跑绿了验的不是现在的系统。

一句话口径也同步改了：**场景 / 录像 / 用例 / 脚本是一条链**（`场景 → 录像（output/llm_cassettes/）→ 用例 → 脚本`），原来只写「场景 → 用例 → 脚本」。

**实测佐证**：`output/llm_cassettes/` 现有 2 份录像（`3cab68f369ce89d5.json` 254KB、`d4335eab08f6ca1f.json` 24KB），它们就是交付物的上游输入，不是缓存。
